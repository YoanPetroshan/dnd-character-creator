# Phase 4c — Feats as a First-Class Mechanic (Slice i: Catalog + Granted Effects): Design

## Context

Phase 4a (sourcebook races) and Phase 4b (sourcebook backgrounds) are both merged to main. Phase 4b's Task 6 imports a background's `feats` field (which feat(s) it grants) into `sheet.grantedFeats` — but explicitly, deliberately **inert**: no catalog of real feats exists, nothing checks prerequisites, nothing applies a feat's mechanical effects. The committed Phase 4 design spec named this "Phase 4c... deferred until 4b's shape reveals how feat-references should be structured" — it now has.

This document scopes the FIRST slice of Phase 4c only. Feats turn out to be the largest, most heterogeneous mechanical surface this project has integrated yet — grounded against the real data (`~/.claude/dnd/.data/official/feats.json`, 305 non-`_copy` records, freshly fetched by extending `chargen/sync.py`'s existing `OFFICIAL_TARGETS` list the same way races/backgrounds were fetched), several dimensions are each individually comparable in complexity to a whole prior phase. Rather than attempt all of it in one plan (which this project's own history shows produces exactly the kind of scope-discovery-mid-execution that grew Phase 4a to 9 tasks and Phase 4b to 9 tasks), this spec deliberately draws a bounded first slice and names everything left for a later slice explicitly.

## What the real data looks like (empirically confirmed)

Field presence out of 305 non-`_copy` feats: `name`(305), `source`(305), `entries`(305), `prerequisite`(224), `category`(197), `ability`(178), `additionalSpells`(86), `skillProficiencies`(12), `resist`(11), `toolProficiencies`(10), `expertise`(7), `languageProficiencies`(7), `armorProficiencies`(6), `repeatable`(5), `senses`(4), `weaponProficiencies`(4), `immune`(2), `conditionImmune`(2), `savingThrowProficiencies`(2), `skillToolLanguageProficiencies`(2).

- **`category`**: `G`(95, General), `O`(35, Origin — these are what backgrounds grant), `EB`(32, Epic Boon), `D`(13, Dragonmark), `FS`(11, Fighting Style), `DG`(9, Dark Gift), `FS:P`/`FS:R`(1 each, Fighting Style subtypes). Backgrounds only ever grant `O` (Origin) feats — confirmed by Phase 4b's own grounding.
- **`ability`**: the SAME `{"choose": {"from": [...], "amount"/"count": N}}` shape already handled for races (Phase 4a Task 2) and backgrounds (Phase 4b Task 4) — sometimes a fixed `{"con": 1}` single bonus instead. "Ability Score Improvement" itself is a real feat in this list (`category: G`, `repeatable: true`) with a `{"choose": {..., "hidden": true}}` shape — the `"hidden": true` flag marking it as the feat that's really just "take a normal ASI instead," confirming this project's earlier hypothesis that feats and the existing ASI mechanism are meant to connect. This connection is explicitly OUT OF SCOPE for this slice (see below).
- **`prerequisite`**: a genuinely wide variety — `{"level": N}`, `{"ability": [{"cha": 13}]}`, `{"level": N, "spellcasting2020": true}`, `{"level": N, "feature": ["Fighting Style"]}`, `{"level": N, "feat": ["initiate-of-high-sorcery|dsotdq|..."]}`, `{"campaign": ["Eberron"]}`, `{"exclusiveFeatCategory": ["D"]}`, `{"other": "No other dragonmark"}`, `{"otherSummary": {"entry": "...", "entrySummary": "Special"}}`. Only `level` and `ability` (a minimum ability score) are structured enough to check programmatically against data this engine already computes; everything else references either narrative context (`campaign`), other feats by a compound id this project doesn't yet track combinatorially (`feat`), a class feature by display name (`feature`), or free text (`other`/`otherSummary`).
- **`expertise`**: a NEW mechanic — double proficiency bonus on a named skill. This engine currently computes a single flat proficiency bonus per character; expertise needs a per-skill override.
- **`senses`**: a NEW field — `{"blindsight": N}`/`{"truesight": N}` etc. Not modeled anywhere in this engine (races' Phase 4a work never needed it — no SRD or sourcebook race trait granted it directly at the RACE level in a way Phase 4a's scope touched; it's new here).
- **`savingThrowProficiencies`**: a NEW mechanic — proficiency in a saving throw from a source OTHER than class (this engine's existing `proficient_save_abilities` is entirely class-derived, per Phase 1's original design).
- **`additionalSpells`**: confirmed significantly MORE heterogeneous than either races' (Phase 4a Task 6, `"innate"` key only) or backgrounds' (Phase 4b, `"expanded"` key only) shapes — feats mix `ability`/`innate`/`known`/`prepared`/`expanded`/`name` keys in 16 distinct combinations across just the records sampled, and several entries use a QUERY-FILTER selector (`{"choose": "level=1|class=Sorcerer"}` — "any level-1 Sorcerer spell," not a literal spell name) rather than a literal spell list. Modeling this properly is a materially larger undertaking than either prior phase's spell handling.
- **`skillToolLanguageProficiencies`**: the SAME field Phase 4b found once on Custom Background/PHB and left undisclosed-but-unhandled ("2 languages, OR 1 language + 1 tool, OR 2 tools") — appears on 2 feats too. Same open question, not resolved by this slice either.

## Scope for this slice (Phase 4c-i)

**In scope, full fidelity:**
1. Full feat catalog import — all 305 real feats, source-qualified ids (matching races'/backgrounds' `slug-source` convention), into a new `Catalog.feats: dict[str, dict]`.
2. Granted-effect conversion and APPLICATION for every feat, covering: ability bonuses (fixed and choice, reusing/generalizing the machinery Phase 4a Task 2 and Phase 4b Task 4 already built), skill/tool/weapon/armor proficiency grants (fixed and choice, reusing Phase 4a Task 3/4 and Phase 4b Task 1/2's machinery directly), language grants (reusing Phase 4b Task 3's machinery), damage resistances/immunities/condition immunities (reusing Phase 4a Task 5's `sheet.damageModifiers`/`conditionImmunities` pattern — a feat's resist/immune/conditionImmune values get ADDED to whatever a race/subrace already granted, not replaced), senses (a NEW `sheet.senses: {blindsight?, truesight?, darkvision?, ...}` field — pure data, no combat computation), expertise (a NEW `sheet.expertiseSkills: string[]` field — which skills get double proficiency bonus; this app computes a snapshot, so a downstream export/UI consumer would need to apply the doubling itself, matching how `sheet.proficiencies` already works), saving throw proficiencies from a feat (added to `proficient_save_abilities`, which currently only ever gets class-derived entries).
3. **Wiring background-granted feats' effects onto the sheet** — this is the direct continuation of Phase 4b's own explicit deferral. A background-granted feat id (already flowing as `sheet.grantedFeats`, inert) now resolves against the new feat catalog and its granted effects apply, exactly as if the player had "picked" that feat (background-Origin feats are never actually a player choice under 2024 rules — they're a fixed grant tied to the background).
4. **Structured prerequisite CHECKING** (not blocking, informational) for the two programmatically-checkable shapes: `level` (compare against total character level, already computed) and `ability` (compare against final ability scores, already computed, threading through the SAME timing consideration the existing multiclass-prerequisite check already solved — `_multiclass_prerequisite_problems`, Phase 3b-i, is the direct precedent to mirror). An unmet structured prerequisite produces a `problems` entry (reusing that same problem-shape convention), gated behind the SAME `usePrerequisites` preference toggle the multiclass check already respects (so a player who's turned off prerequisite enforcement for multiclassing also gets it off for feats — one toggle, one meaning, not two).
5. **Explicit, disclosed non-enforcement of every other prerequisite shape** (`campaign`, `feat`, `feature`, `other`, `otherSummary`, `exclusiveFeatCategory`) — the feat's full prerequisite text still round-trips through `entries` for eventual display, but nothing blocks selection on it. This mirrors Phase 4a's own choice-shaped-Dragonborn-resistance precedent exactly: a genuinely harder case gets a narrow, disclosed, non-blocking treatment rather than either a wrong enforcement or a silently missing one.

**Explicitly OUT of scope for this slice, disclosed:**
- `additionalSpells` in any of its 16 shape combinations — too heterogeneous, involves a query-filter selector this engine has no precedent for resolving. A future slice's own scope.
- The "take a feat instead of a normal ASI" class-level choice (`_asi_choice_templates`, Phase 3a) — genuinely a different, later slice: it needs a real UI-affecting design decision about how an "ASI OR feat" meta-choice is represented in the existing generic Choice model, which deserves its own brainstorm rather than being bolted onto catalog-import work.
- `repeatable`/`repeatableHidden` feat multiplicity (a player taking the same feat twice, e.g. via two separate ASI-or-feat choices) — not reachable yet since the ASI-or-feat connection itself isn't built.
- `exclusiveFeatCategory` prerequisite enforcement (e.g. "no other Dragonmark feat") — needs the same multi-feat-selection tracking `repeatable` needs, deferred with it.
- `skillToolLanguageProficiencies`'s "2 of any combination" shape — same open question Phase 4b left for backgrounds, not resolved here either; affects 2 feats.
- A player-facing "pick a General/Fighting-Style/etc. feat" UI beyond what background-granted feats already surface — this slice makes background-granted feats' EFFECTS real; browsing/selecting from the wider 305-feat catalog directly is a frontend concern for a later slice.

## Architecture

Directly extends the established Phase 4a/4b pattern: `server/catalog/official_source.py` gains `load_official_feats()`, following `load_official_races()`/`load_official_backgrounds()`'s exact shape (source-qualified ids, `_copy` skip — though confirmed 305/305 real feats have no `_copy`, so this is defensive, not load-bearing here). `catalog/loader.py` merges the result into a NEW `Catalog.feats` dict (there is no bundled SRD feats file to merge against — 2014 SRD has no feats at all, a genuinely new, official-data-only catalog dimension; `has_official()` being `False` means `Catalog.feats` is simply empty, and everything downstream that reads it degrades to "no feat effects," which is exactly today's behavior — the safe no-op guarantee holds trivially here since there's no pre-existing feat behavior to preserve).

`engine/resolve.py` gains a new pass, mirroring `_species_ability_bonuses`/`_background_ability_bonuses`'s established pattern: `_feat_granted_effects(catalog, feat_ids)` collects every EFFECT (ability bonuses, proficiencies, resistances, senses, expertise, saving throws) across every feat id in `sheet.grantedFeats`, feeding the SAME early ability-score pass and the SAME `_categorize_proficiency`/`proficient_skills` merge points every other source (species, background, class) already feeds — no new merge architecture, pure additive participation in machinery that already exists.

## Testing strategy

Every claim in this spec is already empirically grounded against the real fetched data (shown inline above) — the implementation plan's own tasks will re-verify at implementation time, per this project's unbroken discipline, but the SHAPE of the work is now known, not speculative. Given how repeatedly Phase 4a/4b's own per-task reviews found that "should need zero resolve.py changes" claims were sometimes right and sometimes wrong, no such claim is made here without flagging it as something to verify, not assume.

## Self-review

- **Placeholder scan:** none — every explicitly-out-of-scope item names WHY it's out of scope and what would be needed to bring it in, not a bare "TBD."
- **Internal consistency:** the prerequisite-checking scope (structured-only, disclosed-non-enforcement for the rest) is stated once and applied consistently across the "in scope"/"out of scope" lists — not contradicted.
- **Scope check:** deliberately narrower than "all of Phase 4c" — explicitly a first slice, with the two largest deferred pieces (additionalSpells, the ASI-or-feat connection) named as this slice's own natural sequel, matching how Phase 4 itself was decomposed into 4a/4b/4c from the start.
- **Ambiguity check:** the `usePrerequisites` toggle reuse (one toggle governing both multiclass AND feat prerequisite enforcement) is an explicit design decision with its rationale stated, not left for the plan to silently decide.
