# The ASI-or-Feat Mechanic: Design

## Context

Phase 4c-ii (background-granted feats' choice-shaped content — ability-bonus/proficiency/language choices — now a real, selectable `Choice`) is merged to main. This is the second, larger of the two user-approved slices (2026-09-28: "Направи малкото и веднага след него голямото" — "do the small one, then immediately the big one"). Feats today are reachable ONLY as a background's fixed or player-chosen grant. This slice makes feats player-SELECTABLE the RAW way: at a class level that grants an Ability Score Improvement (PHB, every class, levels 4/8/12/16/19, plus Fighter's 6/14 and Rogue's 10 — already computed by the existing `_asi_granting_levels`), the player may take a feat instead of the ability-score increase.

No prior design exists for this — unlike 4a/4b/4c-i/4c-ii, which all extended an already-approved high-level design, this is genuinely new. Grounded this session against the real fetched feat data (`~/.claude/dnd/.data/official/feats.json`) and the current `server/engine/resolve.py`/`server/engine/asi.py`/`frontend/src/pages/ClassPage.tsx`.

## Goal

At every ASI-granting level, the player picks EITHER an ability-score increase (today's 7 combos, unchanged) OR one eligible feat — a single decision, matching RAW's own framing ("you can take a feat instead"). Picking a feat applies its full effect set (everything Phase 4c-i's granted-effect machinery already does) and, if that feat itself has choice-shaped content (ability-bonus/proficiency/language), offers those as real, selectable, cascading choices too — reusing Phase 4c-ii's machinery, not rebuilding it.

## Real-data grounding

`catalog.feats` filtered to `category == "G"` ("General," the RAW-eligible pool for this mechanic) has exactly 95 real entries. One of them, `"Ability Score Improvement"` itself, is the 2024/XPHB-era representation of the classic +2/+1-split choice — its own `ability_bonus_options` envelope is structurally the SAME 7-combo shape `asi.py`'s hardcoded `asi_combinations()` already produces. **This app's existing ASI-combo options are kept as the hardcoded SRD-era path (unchanged) and this literal catalog feat is excluded from the feat-options pool by id**, so the player is never shown the identical mechanic twice under two different labels.

Prerequisite shapes among the 95: 34 `level`-only (already fully enforced), 17 `ability`-only or `ability+level` (already fully enforced via the existing `_feat_prerequisite_problems`/`_feat_structured_prerequisite` machinery), the rest (`feat`, `spellcasting2020`, `proficiency`, `featCategory` — 59 total) are non-structured prerequisites this app already discloses-but-never-enforces for background-granted feats (`_feat_structured_prerequisite` returns `None` for these, so `_feat_prerequisite_problems` skips them, never blocking the grant) — this slice inherits that same disclosed policy unchanged, not a new gap.

**A real, newly-reachable combination this slice must handle correctly**: 10 real General feats (Athlete, Charger, Dual Wielder, Grappler, Inspiring Leader, Observant, Polearm Master, Ritual Caster, Sentinel, Speedy) have BOTH an ability-score prerequisite AND a genuinely choice-shaped `ability_bonus_options` field (not just a fixed bonus). `_feat_prerequisite_problems` already subtracts a feat's own FIXED `ability_bonuses` before checking its own prerequisite (Phase 4c-i's Finding 2 fix) but does NOT yet subtract a feat's own CHOSEN ability-bonus-choice delta — today this is harmless (no background ever grants one of these 10 feats), but the moment a player can freely pick, say, Grappler (STR 13 prerequisite, offers a +1 to STR/DEX/CON as part of its own choice) via an ASI level, the same self-bootstrapping bug Finding 2 already fixed for fixed bonuses becomes reachable for choice-shaped ones too. This slice fixes it as part of its own scope (see Task breakdown below), not as a follow-up.

## Architecture

### Approach chosen: one merged Choice per ASI level, feat options folded into it

Considered and rejected: (a) a two-step "ASI or feat?" toggle Choice, THEN a second "which feat?" Choice once "feat" is picked — more UI round-trips, and RAW frames this as one decision, not two; (b) a flat "N feat slots, spend on any ASI-granting occasion" pool, decoupled from specific levels — re-implements the level-by-level bookkeeping `_asi_granting_levels`/`_apply_asi_progression` already do correctly, and is less RAW-faithful (each ASI-granting level really is 5e's own discrete decision point).

`_asi_choice_templates` (unchanged cid `class:{cls_id}:{lvl}:asi`, unchanged `source.kind: "class"`) gets its `options` list extended: the existing 7 ability-combo options, PLUS one option per eligible General feat (94 after excluding "Ability Score Improvement" itself), each option's `id` namespaced `feat:{feat['index']}` (structurally distinct from combo ids like `"str+2"`, so no collision risk) and its `label` set to the feat's name. A feat option is `disabled` with a reason exactly like an over-cap ASI combo already is, when `preferences.usePrerequisites.feats` is on and that feat's prerequisite isn't met (reusing `_feat_structured_prerequisite`/`_feat_prerequisite_alt_met`, not duplicating the check). **This needs zero frontend change to the Choice-rendering itself** — `ClassPage.tsx`'s existing filter (`c.source.kind === "class" && c.id.startsWith(`class:${classId}:`)`) already matches this Choice today, options-list size growing from 7 to ~101 doesn't change its shape, and the generic `<ChoiceCard>`/`<ChoicePicker>` components render any Choice size-agnostically per the app's own established design.

### Cascading sub-choices: resolved within the SAME `resolve()` call, not a new request/response round trip

`resolve()` is a pure, stateless function re-run on the WHOLE draft on every request — so "cascading" is not a client-visible multi-step wizard problem, it's an ordering problem inside one function call: once a level's `class:{cls_id}:{lvl}:asi` selection names a feat, that feat's own choice-shaped content must become new Choices in THIS SAME response, using whatever THIS SAME draft already recorded for them (if anything).

A new pre-pass function, `_resolve_asi_selected_feats(draft, catalog) -> list[dict]`, runs where `_resolve_granted_feats` (background) already runs — early, before the "Final ability scores" section — and does the following per class in `draft.classes`:
1. Compute that class's ASI-granting levels (`_asi_granting_levels`, already pure/re-callable).
2. For each such level, read `class_choices.get(f"class:{cls_id}:{lvl}:asi")`. If it names a `feat:{index}` option (not an ASI-combo id), resolve `catalog.feats[index]`.
3. Attach provenance to the resolved feat dict (`_origin_cid_prefix = f"class:{cls_id}:{lvl}:asi:feat:{index}"`) so every downstream cid this feat's choice-shaped content builds is scoped under ITS class+level+feat, not the bare `feat:{index}:...` background-only shape — this is the origin-scoping Phase 4c-ii's own final review flagged as a future requirement (a feat grantable from two origins would otherwise collide on cid).
4. Also compute, right here, that level's OWN already-recorded ability-bonus-choice selection (if the feat has `ability_bonus_options`): read `class_choices.get(f"{origin_cid_prefix}:ability-bonus")`, resolve via `_feat_ability_bonus_deltas(feat["ability_bonus_options"])`, and combine with the feat's fixed `ability_bonuses` into one total per-level delta.

The results feed TWO places:
- **`resolved_feats` (the existing list background-granted feats already populate)** gets these ASI-selected feats appended, tagged with their origin — every existing downstream consumer (`_feat_proficiency_ids`, `_feat_languages`, `_feat_expertise_skills`, `_feat_saving_throw_proficiencies`, `_feat_senses`, `_species_damage_modifiers`/`_species_condition_immunities`'s `feats` parameter, `_feat_prerequisite_problems`, `sheet.grantedFeats` assembly) already generically handles "every feat in `resolved_feats`" and needs NO changes to consume these — this is the same reuse discipline every prior 4c slice followed.
- **`_apply_asi_progression`** gains one new parameter, `feat_deltas_by_level: dict[int, list[tuple[str,int]]]` (built from step 4 above), so its per-level walk applies EITHER the selected ASI combo's deltas (unchanged) OR, when the level's selection was a feat, that feat's already-computed total delta (fixed + chosen sub-choice) — keeping the cap-checking math exactly where it already correctly lives, not duplicated.

`_feat_choice_templates`/`_feat_ability_bonus_choice_templates` (Phase 4c-ii) each gain one new optional parameter, `origin: str | None = None` — when given (only ever for a single-feat list, the ASI case), the cid is built as `f"{origin}:proficiency-choice-{i}"` / `f"{origin}:languages"` / `f"{origin}:ability-bonus"` instead of the default `f"feat:{feat['index']}:..."`. Background-granted feats keep calling these with `origin=None` (unchanged behavior, unchanged cids, zero risk to Phase 4c-ii's own already-shipped, already-tested coverage). The 3 merge sites that already accept `"feat"` as a `source.kind` need NO further change — they match on `kind`/cid-substring, not on the exact prefix, so an origin-scoped cid still merges correctly.

### Where the cascaded sub-choices render in the frontend

A cascaded sub-choice's cid is `class:{cls_id}:{lvl}:asi:feat:{index}:...` — starts with `class:{classId}:`, matching `ClassPage.tsx`'s existing cid-prefix filter, but its `source.kind` is `"feat"` (mirroring 4c-ii's own convention for a feat's own choice-shaped content), which `ClassPage.tsx`'s current filter does NOT match (`kind === "class"` only). The one required frontend change: widen that filter to `(c.source.kind === "class" || c.source.kind === "feat") && c.id.startsWith(...)`, mirroring EXACTLY the fix Phase 4c-ii's final review already made to `BackgroundPage.tsx` for the same reason. `SET_CHOICE_SELECTION` dispatched with `source: "class"` (unchanged, `ClassPage.tsx` already hardcodes this for every choice it renders) writes into `draft.classes[classId].choices`, which is exactly where `_resolve_asi_selected_feats` and `_apply_asi_progression` already read from — no reducer change needed, mirroring 4c-ii's own finding that no reducer change was needed there either.

### The prerequisite self-bonus fix

`_feat_prerequisite_problems` already subtracts a feat's own fixed `ability_bonuses` before checking its own prerequisite. Extend it to ALSO subtract, for each feat, its own CHOSEN ability-bonus-choice delta if one was selected — this requires the function to receive each feat's already-resolved chosen delta (computed once, during the SAME pre-pass/early pass that already computes `feat_bonuses` for `final_scores` — both background-side and ASI-side choice-shaped ability bonuses already flow through `_feat_ability_bonus_choice_templates`/`_feat_ability_bonus_deltas`, so this is a matter of threading the SAME per-feat delta dict into `_feat_prerequisite_problems` rather than computing it a second time).

## What does NOT change

- `_resolve_granted_feats` (background-side resolution) — untouched, background grants keep working exactly as Phase 4c-i/4c-ii left them.
- `_feat_choice_templates`/`_feat_ability_bonus_choice_templates`'s DEFAULT behavior (no `origin` given) — untouched, existing background-side tests keep passing unmodified.
- The 3 merge sites extended for `"feat"` in Phase 4c-ii — untouched, already generic enough.
- `asi_combinations()`/`asi_exceeds_cap()`/`apply_asi()` in `engine/asi.py` — untouched; the 7 ability-combo options and their cap math stay exactly as they are, feat-selection is a parallel path through `_apply_asi_progression`, not a replacement of the existing one.
- Non-structured feat prerequisites (`feat`/`spellcasting2020`/`proficiency`/`featCategory`) — stay disclosed-but-unenforced, matching the existing, already-shipped policy; not this slice's scope to change.
- `repeatable`/`repeatableHidden`/`exclusiveFeatCategory` — still out of scope (explicitly named as such in the architecture doc since Phase 4c-i). A player COULD in principle select the same non-repeatable feat via two different ASI levels, or via both a background grant and an ASI level — this slice does NOT add duplicate-prevention, disclosed as a known, narrow gap matching this project's established pattern of disclosing rather than silently half-solving.
- `additionalSpells` (16 shapes, includes a query-filter spell selector) — still out of scope.

## Testing strategy

Real data throughout — no synthetic-feat fallback should be needed here, unlike 4c-ii's ability-bonus/language paths, since the ASI-feat pool is the full real 95-entry (94 after exclusion) General category. Concrete real cases, grounded against `~/.claude/dnd/.data/official/feats.json` this session (re-confirm exact fields at plan/implementation time, this data can be re-synced):

- **No choice-shaped content at all** — Actor/XPHB, Crossbow Expert/XPHB, Great Weapon Master/XPHB, Durable/XPHB (confirmed: no `skillProficiencies`/`toolProficiencies`/`languageProficiencies` with a `choose`/`any` shape, no choice-shaped `ability`) selected at an ASI level, applying only fixed effects, no cascaded choices.
- **A genuine `proficiency_choices` (skill) AND a genuine `ability_bonus_options` choice on the SAME feat** — Skill Expert/XPHB (confirmed real shape: `skillProficiencies: [{"any": 1}]`, `ability: [{"choose": {"from": ["str","dex","con","int","wis","cha"]}}]`) — the primary end-to-end cascading case: both of its own sub-choices must appear once Skill Expert is picked at an ASI level, and both must apply on selection.
- **A fixed tool grant plus a choice-shaped ability bonus** — Chef/XPHB (confirmed: `toolProficiencies: [{"cook's utensils": true}]`, a FIXED grant, not a choice, alongside `ability: [{"choose": {"from": ["con","wis"]}}]`) — confirms a feat's fixed content applies immediately (no cascaded proficiency choice) while its choice-shaped ability bonus still cascades correctly, i.e. the two paths don't get conflated.
- **The self-bonus-prerequisite fix** — Grappler/XPHB (STR 13 prerequisite, offers a choice-shaped +1 among STR/DEX/CON): selecting Grappler with a base STR of 12 and choosing its own +1 STR must NOT satisfy Grappler's own STR-13 prerequisite (still flagged, when `usePrerequisites.feats` is on); a base STR of 13 must pass regardless of which ability the player picks for Grappler's own bonus.
- **Multiclass cid collision** — the SAME feat (e.g. Skill Expert) selected at two different classes' ASI levels, or the same class's two different ASI levels, must not collide on cid — both instances resolve, render, and apply independently.
- **The "Ability Score Improvement" exclusion** — confirm the feat-options list for any ASI level never includes an option whose id resolves to the `Ability Score Improvement/XPHB` catalog entry itself.
- **Safe no-op** — a draft with every ASI level still unfilled, or filled with a plain ASI combo exactly as today, must be byte-identical against every existing ASI-related test — the single most important regression guard, since this slice touches `_apply_asi_progression`, load-bearing code every existing multiclass/leveling test already depends on.
