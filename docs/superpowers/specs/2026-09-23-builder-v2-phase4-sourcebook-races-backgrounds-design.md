# Phase 4a — Sourcebook Races & Backgrounds: Design

## Context

The v1 archive (`chargen/`, ported verbatim into this repo since Phase 1, never modified) already has working infrastructure for fetching the WIDER, multi-sourcebook official D&D dataset — NOT just the free SRD. `chargen/sync.py --official` fetches `races.json`/`backgrounds.json` from `5etools-mirror-3/5etools-src` (the community-maintained, MIT-licensed mirror of 5etools' own structured data — the same dataset the whole D&D digital-tools community builds on). This data is **already fetched on this machine** (confirmed: `~/.claude/dnd/.data/official/races.json` — 553KB, 160 race records; `backgrounds.json` — 686KB, 161 background records), spanning roughly 20 sourcebooks per entity type (Volo's Guide, Xanathar's, Tasha's/Mordenkainen's Multiverse, Eberron, Ravnica, Theros, Wildemount, Ravenloft, Fizban's, Sword Coast Adventurer's Guide, and more — confirmed via the real `source` field on every record).

**The critical finding that shapes this whole spec:** `chargen.catalog.Catalog` converts this data into its OWN frozen Python dataclasses (`Race`, `Background`, etc.) — a completely different object model than what v2 uses. v2's `server/catalog/loader.py` reads the raw 2014 SRD JSON dict shapes **directly**, and `server/catalog/choices.py`/`server/engine/resolve.py` read those same raw dict shapes throughout (e.g. `race["ability_bonuses"]`, `race["traits"]`, both plain dicts matching the 5e-bits SRD JSON's own field names). **v1's `Catalog` dataclasses are not directly usable by v2's engine — wiring them in would require rewriting `resolve()`/`choices.py` to consume a different object model, which is a much bigger, riskier change than the actual goal here.** The reusable part of v1's work is the DATA SOURCE (the fetch script, the URL, the MIT license already established as safe) and the NORMALIZATION KNOWLEDGE embedded in `chargen/normalise.py`'s `race_from_5etools`/`background_from_5etools` functions (what fields exist, what they mean) — not their Python output types.

**The actual task, precisely stated:** write NEW normalizer functions, native to v2, that convert the raw 5etools-src race/subrace/background JSON records into the **same dict shape** v2's engine already expects (matching the 2014 SRD JSON's own field conventions) — so that `catalog/choices.py`/`engine/resolve.py` need **zero changes** to consume them. The wider catalog becomes, from the engine's point of view, just... more entries in the same `races`/`subraces`/`backgrounds` dicts it already has.

## Goal

Every race, subrace, and background from every official WotC sourcebook (as covered by the 5etools-src dataset) becomes selectable in the builder, with the SRD baseline (2014 free content, already fully supported) untouched and unchanged in behavior. A player can see which BOOK a given race/background comes from (matching D&D Beyond's own UI convention, confirmed from the user's own reference captures of D&D Beyond's builder — races/classes are grouped and labeled by source book), and can choose which sources are "on" for their character (reusing `Draft.sources: string[]`, a field that has existed in the Draft type since Phase 0 but has never been read by `resolve()` — confirmed by direct grep).

## Non-goals (explicitly out of scope for this spec)

- **Classes, subclasses, spells, equipment from other sourcebooks.** The 5etools-src `sync.py --official` fetch deliberately does not even download `class/*.json`/`spells/sources.json` (v1's own documented scope cut — no normalizer exists for those shapes, 2014 SRD already covers the classes the campaign actively uses). Extending to these is real, separate future work — a different, larger effort (class/spell records are far more mechanically complex and numerous than races/backgrounds), tracked as its own future phase, not bundled into this one.
- **Full mechanical modeling of every non-SRD race's unique traits.** This is the single biggest scope-control decision in this spec — see "Mechanical fidelity tiers" below.
- **2024 ("5.5e"/"XPHB") content as a separate ruleset toggle.** The 5etools-src data already includes 2024-edition records (tagged `XPHB` in `source`) mixed in with everything else — they're just MORE entries in the same wider pool, labeled by their own source like any other book. This spec does NOT build a distinct "2014 vs 2024 ruleset" switchboard (that's a materially different feature — a global rules-version toggle affecting classes/mechanics broadly, not just which races/backgrounds are visible). XPHB races/backgrounds get imported and labeled like any other source in this pass; a dedicated "which ruleset" toggle is future work if wanted.

## Mechanical fidelity tiers — the key scope-control decision

Empirically confirmed: a real non-SRD race record (e.g. Aasimar from Volo's Guide) has meaningfully MORE and MESSIER mechanical surface than an SRD race:

- **Tier 1 — fully mechanical, same as SRD races today:** ability bonuses (including the ~6 records using a `choose N from {...}` shape — confirmed via direct scan — reusing the EXACT SAME `ability_bonus_options` choice mechanism already built for Half-Elf in Phase 3b), speed, size, fixed language grants. These map cleanly onto v2's existing dict shape and existing engine logic with no new mechanism needed.
- **Tier 2 — descriptive only, NOT mechanically computed:** trait text (5etools' `entries` array — a mix of free-form prose entries like "Age"/"Size" alongside real mechanical traits like "Celestial Resistance", with no separate structured Traits.json the way SRD has one). These get shown on the sheet as read-only flavor text (name + description), but do NOT feed into `derived`/`proficiencies`/any computed field. This differs from SRD races, where certain traits (e.g. Elf's Keen Senses) DO grant a real, computed skill proficiency via a structured `proficiencies` field on the trait — the wider dataset has no equivalent structured field for this, so automatic proficiency grants are an SRD-only mechanic for now.
- **Tier 3 — explicitly deferred, not built at all:** damage resistances/immunities (`resist`/`immune` fields — confirmed present, e.g. Aasimar's necrotic/radiant resistance), innate spellcasting (`additionalSpells` — confirmed present, e.g. Aasimar's Light cantrip), and any other bespoke mechanical hook a specific race/background needs. **v2's `derived`/`sheet` shape has no field for damage resistances or innate racial spells AT ALL today** (single-class or multiclass) — building that is real, separate engine work with its own design questions (how do innate spells interact with `sheet.spells`? do resistances get a new `derived` field?), not a natural extension of "import more races." Explicitly flagged, not silently dropped: any race/background record with content in these fields still imports fine for Tier 1/2 purposes, it just means that SPECIFIC mechanical bonus isn't modeled yet — matching this project's established pattern of "narrow, disclosed cuts" rather than blocking on 100% fidelity.

This tiering is the single most important judgment call in this spec — confirm it matches what's actually wanted before implementation starts, since it determines how "complete" a Tasha's or Volo's race feels on the sheet (real numbers for ability/speed/languages, readable flavor text for the rest, silence on resistances/innate spells).

## What the normalizer needs to produce

Read `server/catalog/loader.py`'s current `Catalog` dataclass and the real 2014 SRD JSON shape for `races`/`subraces`/`backgrounds` (both already loaded and working) as the TARGET shape. The new normalizer (a new module, candidate name `server/catalog/official_source.py` or similar — exact naming a plan-writing decision) reads `~/.claude/dnd/.data/official/races.json`/`backgrounds.json` (via `chargen.sources.official_dir()`/`has_official()` — REUSE these two functions directly, they're pure path/existence helpers with no v1-specific object-model coupling, confirmed by reading `chargen/sources.py` in full) and produces dicts shaped exactly like the existing SRD race/subrace/background dicts: `index`, `name`, `ability_bonuses` (or `ability_bonus_options` for the choose-N shape), `speed`, `traits` (a list of trait references — but see below), `languages`, `starting_proficiencies` (background), etc.

**Trait representation for Tier 2:** SRD traits are a two-step reference (`race["traits"] = [{"index": "keen-senses", ...}]`, resolved against a separate `catalog.traits["keen-senses"]` dict with the full trait record, including the structured `proficiencies` field). For imported sourcebook races, mint a synthetic trait entry per `entries` item (a generated `index` like `"aasimar-celestial-resistance-vgm"`, `name`, and description text), added to the SAME `catalog.traits` dict SRD traits already live in — but WITHOUT a `proficiencies` field (or with one only where a future task adds real parsing for it), so the existing trait-rendering code path (already built, already tested) picks them up automatically as descriptive traits, while `resolve()`'s existing "does this trait grant a skill" check (which already correctly handles traits with no `proficiencies` field, per Phase 3b-i's fix) correctly finds nothing to grant for them.

## Source labeling and selection

- Every imported race/subrace/background record carries its own source book (5etools' own `source` field — e.g. `"VGM"`, `"XPHB"`, `"PHB"`) — expose this on the catalog endpoint (`GET /api/catalog`) so the frontend can group/label options by book, mirroring the exact grouping pattern the user's own D&D Beyond reference screenshots show (a collapsible "book" heading with its races/classes listed under it — see `Resurses/Character Builder - CLASS.pdf`, `Resurses/Character Builder - Species.pdf` for the visual reference to build the frontend grouping against, once this phase's data plumbing lands and a UI task is scoped).
- **Confirmed already existing, never wired up:** `Draft.sources: string[]` — reuse this field as "which source books this character is allowed to draw from." `resolve()` gains a filter step: when `draft.sources` is non-empty, only records whose `source` is in that list (plus the SRD baseline, always available) are considered valid selections — an unrecognized/filtered-out `raceId` in the Draft produces the SAME `unknown-species` problem the engine already raises for a genuinely-nonexistent id (no new problem type needed). When `draft.sources` is empty/absent, ALL sources are available (the permissive default, matching "nothing has been restricted yet").
- Full source-picker UI (a real "which books are you allowed to use" settings screen, matching the Preferences pattern from Phase 3a's follow-up work) is likely its OWN follow-up task within this phase's plan, not assumed to be free — scope explicitly at plan-writing time.

## Licensing note (carried over from v1, re-confirmed, not re-litigated)

`chargen/sync.py`'s own docstring already documents this data as sourced from `5etools-mirror-3/5etools-src`, describing it as MIT-licensed, and v1 already made the deliberate choice to store it OUTSIDE the repo (never committed) specifically because it's a wider, community-maintained mirror rather than WotC's own first-party SRD release — this project inherits that same caution rather than re-deciding it. This phase does not change that storage decision: the fetched data stays at `chargen.sources.official_dir()` (outside the repo), and v2's new normalizer reads from there at catalog-load time, same as v1 already does, never bundling it into `server/catalog/` or committing it to git.

## Testing strategy

- Every new normalizer function tested against the REAL fetched data (already present on this machine) — this project's standing discipline, no hand-typed fixtures standing in for real records.
- A regression check: with the official data ABSENT (simulating a fresh machine that hasn't run the fetch — `chargen.sources.has_official()` returns `False`), the catalog and every existing test behaves EXACTLY as it does today — a safe no-op, mirroring `chargen.catalog.Catalog`'s own already-proven `_merge_official()` no-op guarantee.
- At least one full end-to-end resolve() test building a character with a non-SRD race (e.g. Aasimar) and a non-SRD background, confirming ability bonuses/speed/languages compute correctly and Tier-2 traits appear on the sheet as descriptive text.
- A `draft.sources` filtering test: a race from a source NOT in `draft.sources` is correctly rejected as `unknown-species` (or however the exact problem manifests once implemented).
