# Phase 3b-i — Multiclassing Core: Design

## Context

Phase 3a (single-class leveling 1-20) shipped `resolve()`'s per-class computation as a set of small, already-parameterized helpers — `_class_choice_templates(cls, cls_id)`, `_cumulative_feature_refs(catalog, cls_id, subclass_id, max_level)`, `_asi_granting_levels(catalog, cls_id, max_level)`, `_spell_choice_templates(...)`, etc. — each one takes a single class's data and returns that class's own templates/refs. `resolve()` itself currently calls each of these exactly once, against `classes[0]`, and explicitly rejects more than one entry in `draft.classes` with a `multiclass-unsupported` problem (`resolve.py:472-474`).

This is the first of two sub-phases (3b-i, 3b-ii) implementing D&D 5e multiclassing per the architecture spec (§10, Phase 3: "multiclassing (incl. multiclass spell-slot table)"). **3b-i** covers: adding/removing classes, each class's own independent progression (features, ASIs, spell choices — reusing the existing per-class helpers unchanged, called once per class instead of once total), the level-vs-total-level distinction (proficiency bonus, HP), multiclass-specific proficiency grants, and prerequisite enforcement. **3b-ii** (a separate spec/plan, after this one ships) covers the combined multiclass spell-slot table — deliberately isolated since it's the highest-risk, most RAW-fiddly part, and depends on 3b-i's "multiple classes exist" foundation already being solid.

## Goals

- A character can have 2+ classes (`draft.classes` already an array — Phase 3a code artificially collapses it to one entry).
- Each class levels and grants features/ASIs/spell-choices **independently**, using the exact same per-class logic Phase 3a already built — no new feature/ASI/spellcasting logic, only a loop instead of a single call.
- **Proficiency bonus** derives from **total character level** (sum across all classes), not any single class's level.
- **HP** correctly applies 5e's "only your very first class level ever takes the hit die's max; every level after that — including your *first* level in every class you multiclass into later — uses the roll/average method." This is a common correctness bug in DIY builders and is called out explicitly as a design requirement, not left implicit.
- **Multiclass proficiency grants**: a class taken as a second-or-later class grants only its `multi_classing.proficiencies` (already present in the bundled SRD data, verified empirically — a smaller list than the full level-1 grant), not the full starting proficiency list. Only the first class in `draft.classes` gets the full level-1 grant.
- **Equipment**: multiclassing grants no additional starting equipment — this stays anchored to the first class only (already effectively true in the current code, this task makes it an explicit, tested invariant rather than an accident of "only one class exists").
- **Prerequisites**: when `draft.preferences.usePrerequisites.multiclass` is on, adding or keeping a class requires the character's **final ability scores** (post species/background/ASI — the same `final_scores` Phase 3a already produces before class resolution) to meet that class's `multi_classing` requirement, and simultaneously requires every **other already-taken class's** requirement to still be met. A failure is a `problem`, never a hidden/removed option — matching the architecture spec's explicit rule (§4a) and this project's established `disabled`/`disabledReason` pattern for softer gates.

## Non-goals (explicitly deferred)

- The multiclass spell-slot table (combined caster level → shared slot pool) — **3b-ii**.
- Pruning/warning when removing a class invalidates other selections — **Phase 3c** ("pruning warnings"), per the architecture spec's own phasing. Removing a class in 3b-i behaves exactly like Phase 3a's existing "level-down leaves stale selections inert" behavior: a removed class's own choice templates simply stop being generated, so their old selections in the Draft are never read again — never deleted, never corrupted, just inert. No new pruning logic.
- A hard UI cap on the number of classes is NOT a backend concern — the engine handles however many entries `draft.classes` contains (validated only for total level ≤ 20); if the frontend wants to cap the "+ Add Another Class" button at some N, that's a frontend-only decision made during the plan, not a backend rule.
- 2024-ruleset multiclassing differences (if any) — out of scope; this project targets 2014/SRD 5.1 rules until Phase 4.

## Data model changes

**`Draft.classes: ClassSelection[]`** — no shape change. The array already supports multiple entries; only `resolve()` and the frontend currently assume length ≤ 1.

**New reducer actions** (`frontend/src/DraftContext.tsx`):
- `ADD_CLASS { classId: string }` — appends a new `ClassSelection` entry (`{classId, level: 1, choices: {}}`) if `classId` isn't already present in `draft.classes` (silently no-ops on a duplicate — the UI should already grey out already-taken classes, this is defense in depth, not the primary guard).
- `REMOVE_CLASS { classId: string }` — removes the matching entry from `draft.classes`.
- Every existing per-class action (`SET_CLASS_LEVEL`, `SET_SUBCLASS`, `SET_HP_ROLL`, and `SET_CHOICE_SELECTION` when `source === "class"`) changes from implicitly targeting `classes[0]` to taking an explicit `classId` and updating the matching entry in the array. This is a breaking change to those four actions' payload shape — consistent with this project's established precedent of non-backward-compatible Draft-shape changes across every prior phase (no migration path needed, `localStorage` drafts from before this ships will need a manual clear, exactly as happened for Phase 3a's spell-choice-id change).
- `SET_CLASS` (picking the FIRST class) stays as-is conceptually but its meaning narrows to "replace `classes[0]`" — it's really "set primary class," distinct from `ADD_CLASS` which appends. (The plan should double check whether renaming `SET_CLASS` → something like `SET_PRIMARY_CLASS` reads more clearly, given it now has a sibling `ADD_CLASS` — a naming call for plan-writing time, not a spec-level decision.)

## `resolve()` changes

**Validation.** Replace the current `if len(classes) > 1: problem + truncate` block with:
- Each entry's `level` still individually clamped/validated 1-20 (unchanged per-entry logic).
- A new check: `sum(level for each class) > 20` → a `total-level-exceeded` problem (20 is 5e's designed level cap; the engine doesn't silently truncate — mirrors the "never hide, always surface a problem" philosophy already established).
- Duplicate `classId` entries in the array → a `duplicate-class` problem, and only the first occurrence is used (defense in depth again — the frontend should prevent this, but the engine must never crash or silently double-count a repeated class).

**Per-class loop.** Where `resolve()` currently computes once against `cls_entry = classes[0]` (`resolve.py:476` onward through the choice-template assembly around line 597), this becomes a loop over `classes`, calling the SAME Phase 3a helpers per entry: `_class_choice_templates`, `_cumulative_feature_refs`, `_feature_choice_templates`, `_asi_granting_levels`/`_apply_asi_progression`/`_asi_choice_templates`, `_spell_choice_templates`. Each entry's own `cls_id`/`level`/`subclass_id` feed these exactly as `classes[0]`'s did before — no per-helper logic changes, only the calling loop.

**ASI progression across multiple classes.** `_apply_asi_progression` currently threads a single class's ASI-granting levels through the ability-score pipeline in level order. For multiclass, ASI levels are gathered per-class (each class has its own 1-20 progression of ASI-granting levels, from `_asi_granting_levels`), then processed **in `draft.classes` array order** (class 0's ASIs first, then class 1's, etc.) — not interleaved by "historical" level-up order, since the Draft only records each class's *current* level, never the order levels were taken in. This is a deliberate, explicit simplification worth calling out: it's a reasonable, deterministic interpretation (not a RAW violation — RAW doesn't actually prescribe simultaneous vs. sequential resolution order for two classes' ASIs reaching the same effective point), and matches Phase 3a's own "never iterate to a fixpoint, single deterministic pass" philosophy from the architecture spec.

**Proficiency bonus.** Currently read from `catalog.class_level_row(cls_id, level)["prof_bonus"]` — a single class's level row. Proficiency bonus is standardized by *total* character level in 5e (identical progression regardless of class mix), so this becomes `catalog.class_level_row(<any class present>, total_level)["prof_bonus"]` — reading the prof-bonus column, which is class-agnostic, from any available class's level table at the *total* level. **Confirmed empirically** (scanning every class-level row in the bundled `5e-SRD-Levels.json`, grouped by level, excluding subclass-feature rows): `prof_bonus` is identical across every class at every level, zero mismatches — the class-agnostic assumption holds against the real data, not just RAW expectation.

**HP.** `hit_point_max_at_level` (in `server/engine/derived.py`) currently computes one class's HP curve, taking the max-at-level-1 rule for granted at that class's own level 1. For multiclass, HP must sum across classes, where **only the very first class levels EVER get the max-at-level-1 rule — every other class's own level 1 (when multiclassing into it) uses the roll/average method like any level above 1.** This requires either: (a) a new function `hit_point_max_multiclass(classes: list[...], hp_type, hp_rolls) -> int` that iterates all classes, applying the "is this the very first class in the very first slot" check only once at the true start, or (b) treating class 0's level 1 specially and every other level (across every class, including secondary classes' own level 1) via the existing per-level roll/average helper. Exact function shape is a plan-writing decision; the RAW rule itself is the fixed requirement.

**Proficiencies.** `proficient_skills`'s class-sourced portion (`resolve.py:709-712`, currently reading `c["source"]["kind"] == "class"` selections from ALL class choices — already correct, no per-class distinction needed there since it just reads whatever skill-choice selections exist). The NEW piece: fixed multiclass proficiency grants apply for every class in `classes[1:]` (every class after the first), read from that class's `multi_classing.proficiencies` field — separate from and in addition to the full level-1 `cls.get("proficiencies", [])` grant that continues to apply ONLY to `classes[0]`. **Confirmed empirically** (scanning every class's `multi_classing.proficiencies` in the bundled data): every entry is an armor, weapon-category, specific-weapon, or tool proficiency (e.g. `light-armor`, `simple-weapons`, Monk's `shortswords`, Rogue's `thieves-tools`) — never a `skill-` prefixed entry, confirming these never overlap with the skill-proficiency machinery. This data currently has nowhere to land in the sheet (armor/weapon/tool proficiencies aren't surfaced anywhere in `sheet.proficiencies`, which today only has `skills`/`savingThrows`/`languages`). **Recommendation: add an `armor`/`weapons`/`tools` field to `sheet.proficiencies` now** — a direct, mechanical extension of the existing dict shape; leaving newly-computed-but-invisible data around is worse than the small scope addition. Note the level-1 grant for `classes[0]` ALSO includes non-skill proficiencies (`cls.get("proficiencies", [])` — already loaded, just never split out by category before) — so this new sheet field should be populated from BOTH the primary class's full grant AND every secondary class's `multi_classing.proficiencies`, not just the multiclass-specific ones, to be a complete, non-misleading list. (Ranger's `multi_classing.proficiency_choices` — a genuine CHOICE, not a fixed grant, the only such case in the bundled data — needs its own choice template, mirroring `_class_choice_templates`'s existing skill-choice pattern but scoped to armor/weapon proficiency options instead of skills.)

**Equipment.** `_equipment_choice_templates`/`_fixed_equipment` calls for the class source stay anchored to `classes[0]` only (`cls = catalog.classes.get(classes[0].classId)`) — explicit, tested, not incidental.

**Subclass/feature choice ids.** Already scoped by `cls_id` (`class:{cls_id}:{level}:...`), and since a class can only appear once in `draft.classes` (enforced by the new duplicate-class validation above), no id collisions arise from multiclassing — no change needed to the id scheme itself.

**Prerequisites.** A new validation pass, run after `final_scores` is computed (same point in the pipeline Phase 3a's ASI progression already runs) and only when `draft.preferences.usePrerequisites.multiclass` is true: for the FULL set of classes in `draft.classes`, check each one's `multi_classing.prerequisites` (a plain list — ALL must be met) or `multi_classing.prerequisite_options` (an options-array choice — Fighter is the only bundled-data class using this shape, "meet N of these" with `choose: 1` from STR/DEX) against `final_scores`. Any class failing its own requirement produces a `problem` (e.g. `id: "multiclass-prerequisite-unmet-{cls_id}"`) — the class stays in the sheet, its features/levels stay fully resolved, this is purely an informational flag matching the architecture spec's "problem, not hidden option" rule. When the preference is OFF, this entire check is skipped (no problems ever generated) — matching how `usePrerequisites.feats` presumably will (in a later phase touching feats) gate an analogous check.

## Testing strategy

- Every new/changed helper tested against REAL bundled SRD data (this project's standing discipline) — a genuine two-class character (e.g. Fighter 3 / Wizard 2, total level 5) resolved end-to-end, asserting: prof bonus = 3 (from total level 5, not either class's own level), HP correctly sums class 0's max-at-1 plus every subsequent level (including Wizard's own "level 1") via roll/average, Fighter's full level-1 proficiencies present (`sheet.proficiencies.armor`/`weapons` includes Fighter's light/medium armor, shields, simple/martial weapons), Wizard's `multi_classing.proficiencies` grant NOT applicable here (Wizard's own `multi_classing.proficiencies` is empty in the bundled data — confirmed empirically), equipment only reflects Fighter's kit (not Wizard's). A second scenario (e.g. Fighter 2 / Rogue 3) should exercise a secondary class that DOES have a non-empty `multi_classing.proficiencies` grant (Rogue → `light-armor`, `thieves-tools`) to confirm that path.
- A Fighter/Monk prerequisite scenario (Monk needs BOTH DEX 13 and WIS 13 — the "all must be met" shape) and a Fighter-as-secondary-class scenario (STR-OR-DEX choice shape) each tested with prerequisites on and off.
- A regression check that a SINGLE-class draft (today's only supported shape) still resolves identically to before this phase — every Phase 3a test must keep passing unchanged, since single-class is just the `len(classes) == 1` case of the new general loop.

## Self-review

- **Placeholder scan:** none — every requirement above names its exact data source, exact function, or exact bundled-data field. The two facts this design depends on (prof-bonus is class-agnostic; `multi_classing.proficiencies` never contains a skill) were verified directly against the bundled SRD JSON while writing this spec, not assumed from RAW knowledge.
- **Internal consistency:** the "problem, not hidden option" prerequisite rule is stated once and referenced consistently with 3a's and the architecture spec's own established language, not contradicted anywhere else in this doc.
- **Scope check:** deliberately excludes the spell-slot table (3b-ii) and pruning (Phase 3c) — both named explicitly as non-goals with a one-line reason each, not left ambiguous.
- **Ambiguity check:** the ASI-ordering-across-classes decision (array order, not historical order) is flagged as a deliberate simplification with its rationale spelled out, not left for the plan to silently pick.
