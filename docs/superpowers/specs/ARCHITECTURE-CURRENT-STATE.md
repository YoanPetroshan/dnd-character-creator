## What this app is

A from-scratch rebuild of a D&D 5e (2014/SRD 5.1 ruleset) character-creator web app. Separate repo from an earlier "v1" (a different, older character builder in a sibling repo, `dnd-app-bg` — not this one). Python/Flask backend, React/TypeScript (Vite) frontend, no database — the character being built lives entirely in the browser's `localStorage` as a JSON "Draft," and the server is a pure, stateless function: `POST /api/resolve` takes a Draft, returns a fully-computed "Resolution" (derived stats, resolved choices, problems, warnings). Every screen re-POSTs the whole Draft and re-renders from the fresh Resolution — there is no incremental/patch API.

## Core data flow

```
Draft (JSON, in browser localStorage)
  → POST /api/resolve
  → resolve(draft, catalog) in server/engine/resolve.py
  → Resolution: { sheet, choices, derived, problems, warnings, pruned }
  → rendered by the frontend, or fed into an export renderer
```

- **`Draft`** (`frontend/src/types.ts`): what the player has chosen so far. Includes `name`, `sources`, `preferences` (hitPointType/advancementType/usePrerequisites), `classes: ClassSelection[]` (now a real array — see Multiclassing below), `background`, `species`, `abilities`, `equipment`, `details`.
- **`Resolution`**: `sheet` (the finished character — name/level/classes/background/species/abilities/proficiencies/equipment/spells/details), `choices` (every pending-or-resolved Choice, generic across every source), `derived` (ability modifiers, prof bonus, HP, AC, saves, skills, passive perception, `spellSlots`/`warlockSpellSlots` — see Multiclass Spellcasting below), `problems` (blocking issues — e.g. unknown class, over-selected choice), `warnings` (non-blocking — e.g. an equipment envelope that couldn't be represented), `pruned` (as of Phase 3c: one entry per selection that's still sitting in the Draft but no longer reachable — e.g. an ASI tied to a level the player leveled back down from, or a feature choice tied to a subclass the player cleared — see "Pruning" below; NOT populated for the case where a choice's id survives a level-down but its allowed count shrinks, e.g. a spellcaster's known-spells choice — that's a known, separate gap, tracked as follow-up work).
- **The generic Choice model**: every player decision — a class skill pick, a spell choice, an ASI, starting equipment — is represented the same way: `{id, source, label, description, count, options, selected, status}`. `resolve()` builds a `choice_templates` list from every source (class/background/species/equipment/ASI/spells), then applies whatever the Draft already submitted to produce the final `choices` list. The frontend's `<ChoiceCard>`/`<ChoicePicker>` components render ANY choice generically — new choice-producing features (like multiclass proficiency choices) need zero new frontend rendering code, only a new template-building function on the backend.

## Where the rules data comes from

`server/catalog/loader.py` loads the bundled SRD JSON (`chargen/data/srd/*.json` — the SAME data files the OLD "v1" `chargen` module uses, ported verbatim in Phase 1, never modified) into a `Catalog` dataclass: `classes`, `levels`, `features`, `subclasses`, `races`, `subraces`, `traits`, `backgrounds`, `items`, `spells` — each indexed by its SRD `index` field. As of Phase 4a, `races`/`subraces`/`traits` are ADDITIVELY merged with data from official sourcebooks (see "Sourcebook data (Phase 4a)" below) — everything else (`classes`, `backgrounds`, `items`, `spells`, etc.) is still SRD-only; no 5etools adapter exists for those yet, and no 2024-ruleset content has been imported (XPHB races import as just another labeled source, not a separate ruleset switchboard).

Where the bundled SRD data doesn't structurally carry an answer the engine needs (e.g. which ability governs which skill, which classes are half-casters), `server/catalog/reference_data.py` hardcodes it as an open 5e RAW fact, always with a comment explaining why it couldn't be read from the data.

## Sourcebook data (Phase 4a)

As of Phase 4a, ~160 races and ~92 usable subraces from official D&D sourcebooks (Volo's, Xanathar's, Mordenkainen's, Tasha's, Eberron, and ~15 more) are selectable alongside the 9 bundled SRD races, with full mechanical fidelity: ability bonuses (fixed, choice, and a "choose N of any skill/tool" wildcard), skill/tool/weapon/armor proficiencies (fixed grants and player choices), damage resistances/immunities/vulnerabilities, condition immunities, and innate spellcasting (93/102 real innate-spell references resolve against the bundled SRD spell list; the rest degrade gracefully — spell name shown, `spellId: null` — since this app hasn't imported non-SRD spell data).

**Where the raw data lives:** a separate v1 tool (`chargen/sync.py --official`, not part of this app's own code, ported verbatim from an earlier project) fetches `races.json`/`backgrounds.json` from `5etools-mirror-3/5etools-src` (MIT-licensed) into `chargen.sources.official_dir()` — by default `~/.claude/dnd/.data/official/`, deliberately OUTSIDE this repo, never committed, and respecting `DND_CAMPAIGN_ROOT`. `chargen.sources.has_official()` checks whether it's been fetched on a given machine. **This is a real prerequisite a fresh environment won't have by default** — without running that sync command once, `catalog.races` contains only the 9 bundled SRD races, and every sourcebook-race test in the suite is `skipif`-gated on `has_official()` and silently skips.

**The new module:** `server/catalog/official_source.py` (~800 lines) converts the raw 5etools-shaped JSON into the EXACT same dict shape `catalog/loader.py` already produces for SRD races/subraces/traits — so `catalog/choices.py` and `engine/resolve.py` need zero changes to CONSUME sourcebook races (they already read "the SRD shape" generically). This module is also the SINGLE place in the entire codebase allowed to `import chargen.sources` directly — `chargen` lives at the repo root, a sibling of `server/`, and every real way this app runs (`cd server && python app.py`, `cd server && pytest`) has `server/` as its working directory, which does NOT put the repo root on `sys.path`; `official_source.py` patches `sys.path` at import time and re-exports `official_dir`/`has_official`/`load_official_races`, and every other file (including every test) imports those three names from `catalog.official_source`, never from `chargen.sources` directly. A stray direct import elsewhere is a real, reproducible `ModuleNotFoundError`, not a style nit.

Each sourcebook record's id is source-qualified (e.g. `aasimar-vgm`, `aasimar-mpmm`, `aasimar-xphb` — the same monster/race can be reprinted across multiple books, each a genuinely distinct record) — SRD ids have no such suffix, so collision is structurally impossible. `_copy`/`_mod`-based 5etools records (their own "defined as another record plus a diff" shorthand) are skipped entirely, a disclosed, bounded cut.

**`Draft.sources: string[]`** (existed since Phase 0, never read until Phase 4a) now filters which races are selectable: non-empty means only races whose `source` is in the list (plus SRD, always available) resolve; empty/absent means everything is available. **The real frontend default is `[]`** (`frontend/src/DraftContext.tsx`'s `emptyDraft.sources`) — it was briefly `["srd"]` during this phase's own review (a stale Phase-0 placeholder that would have silently made every sourcebook race unselectable the moment this shipped, caught and fixed before merge). No source-picker UI exists yet — `GET /api/catalog` exposes each race's `source` field for a future frontend task to group by book, but today every race is shown regardless of `sources` (the filter is enforced only in `resolve()`, not in what the picker lists).

**Two real, pre-existing bugs surfaced and fixed during this phase** (not introduced by it — both affected bundled SRD races since the app's inception, only ever caught because this phase's own new tests happened to exercise a code path nothing had tested before): `engine/resolve.py`'s trait-proficiency scanning only ever forwarded `skill-` prefixed ids from race/subrace traits into the sheet — tool/weapon/armor grants (e.g. SRD Dwarf's own "Dwarven Combat Training") and race-sourced proficiency CHOICES (e.g. SRD Half-Elf's own "Skill Versatility") never reached `sheet.proficiencies`, for any race, ever, until fixed. Both fixes reuse existing machinery (`_categorize_proficiency`, `build_choice_template`) with small, targeted additions — see `server/engine/resolve.py` directly for the current shape, not this doc, since it will drift.

**New `sheet` fields added this phase, currently with NO frontend consumer** (backend-only, visible via raw `/api/resolve` JSON, not yet rendered anywhere a player sees, and not yet in `markdown_export.py`/`pdf_export.py`): `sheet.damageModifiers: {resistances, immunities, vulnerabilities}`, `sheet.conditionImmunities`, `sheet.innateSpells`.

Phase 4a deliberately did NOT touch: classes/subclasses/spells/equipment-items from other sourcebooks (v1 never built normalizers for these either — a future phase's own scope); backgrounds (Phase 4b, now complete — see below); Feats as a mechanic (Phase 4c, not yet started, deliberately deferred until 4b's shape revealed how feat-references should be structured — it now has, see below); a distinct 2014-vs-2024 ruleset toggle; subrace-level source filtering (only the parent race's source is checked — a subrace from an unlisted book is still reachable today if its parent race's book is listed, a disclosed, narrow gap).

## Sourcebook data (Phase 4b)

Directly extends Phase 4a's architecture — `server/catalog/official_source.py` (now ~1550 lines, races AND backgrounds) gained `load_official_backgrounds()`, following the exact same pattern: converts raw 5etools background JSON into the SRD dict shape `catalog/loader.py` already produces for the bundled Acolyte background, merged additively at load time. `official_source.py` remains the SINGLE place in the codebase allowed to `import chargen.sources` directly — this constraint held across the whole phase (independently re-verified by the final whole-branch review). Backgrounds are structurally simpler than races here: SRD backgrounds carry proficiencies/languages/equipment as direct top-level dict fields, not indirected through a separate "traits" catalog, so no synthetic-trait-minting step was needed.

**What's covered, full fidelity:** skill/tool proficiencies (fixed grants and player choices, including an "any N" wildcard reusing Phase 4a's `any_skill`/`any_tool` machinery unmodified), fixed and choice language grants (the wildcard case reuses SRD's own pre-existing `language_options`/`resource_list` mechanism verbatim — zero new code), the real 2024 background ability-score-improvement rule (every one of 60 real records offers the SAME universal choice — "+2/+1 split between two of a named 3-ability pool" or "+1 to all three," 7 selectable options total, not a per-background varying mechanic — verified exhaustively), the starting-equipment "choose package A or B" shape (reusing the existing `"multiple"` option-bundling mechanism), starting gold (both a fixed `starting_gold` field — which, it turned out, had NEVER been read by this app for ANY background including bundled SRD, an old gap predating this whole plan — and gold from a selected equipment bundle), non-catalog ("narrative") equipment items no longer silently dropped, and inert feat storage (`sheet.grantedFeats` — pure data pass-through, explicitly no prerequisite checking or effect application, deferred to a future Phase 4c).

**Explicitly out of scope, disclosed:** the `additionalSpells` field's `"expanded"` key (a spell-LIST-EXPANSION mechanic — "these spells count as being on your class's list" — genuinely different from races' `"innate"` spellcasting; nothing in this engine models it); a full narrative-item catalog/registration system (non-catalog equipment items are shown as text, never resolved into real inventory entries); House Agent/ERLW's narrative-context-dependent tool choice (12 dragonmarked-house alternatives, always resolves to the first one, disclosed in a docstring rather than solved); sub-1-gp coinage (a fixed grant of, say, 1 silver piece is simply not tracked — `starting_gold` stays `None` rather than reporting a wrong `0`).

**Process pattern that repeated three times this phase, worth knowing if you're the next reader:** a task's own review found a real, PRE-EXISTING bug in `resolve()`'s consumption of background data (not introduced by that task, only newly surfaced by its own tests) — Task 1 → Task 1b (tool/weapon/armor proficiency grants never reached the sheet, mirroring Phase 4a's Task 3→3b for races), Task 2 → Task 2b (an independent reviewer FORCED a commit split when an implementer fixed a similarly-discovered wiring gap inline instead of disclosing it — this plan's controller had to actually split one bundled commit into two after the fact to preserve the established process), Task 5 → Task 5b (a near-universal, 75/76-real-backgrounds-affected bug where selected gold/flavor/category bundle members were silently dropped, PLUS the starting_gold gap above). The FINAL whole-branch review then found a fourth, larger instance the per-task process couldn't reach at all — fixed equipment/gold for the majority (2014-era) `"_"`-keyed background shape had never been wired up by ANY task (each task's own scope genuinely didn't include it, so no per-task review had reason to look) — closed as part of the final review's own authorized fix wave, which itself introduced and then closed one small regression (a fabricated `0 gp` for two sub-1-gp records) before merge.

## Backend layout (`server/`)

- `app.py` — Flask routes: `/api/health`, `/api/resolve`, `/api/catalog` (+ per-class/background/species detail endpoints), `/api/items`, `/api/spells`, `/api/export/<fmt>` (yaml/markdown/pdf, one parameterized route).
- `catalog/loader.py`, `catalog/choices.py` (generic `build_choice_template`/`build_choice_options` — turns a raw SRD "choose N from X" envelope into a Choice template, handling every `option_type` shape the bundled data uses: `reference`, `counted_reference`, `string`, `multiple`, `ability_bonus`), `catalog/reference_data.py`.
- `engine/resolve.py` (~1000 lines — the heart of the app, see below), `engine/derived.py` (pure HP/modifier/save/skill math, no I/O), `engine/asi.py` (pure ASI combination math), `engine/equipment.py`, `engine/spells.py`.
- `export.py` (YAML), `markdown_export.py`, `pdf_export.py` (via `fpdf2`, with a bundled DejaVu Sans font for Cyrillic support — the UI and exports are Bulgarian-language).
- `tests/` — pytest, run via `server/.venv/bin/python -m pytest`. Currently 455 tests, all passing (a meaningful chunk of these only run — not skip — on a machine that has run `chargen/sync.py --official` at least once; see "Sourcebook data (Phase 4a)" above). A separate repo-root test (`tests/test_chargen_isolation.py`) enforces that nothing outside `chargen/` (the ported v1 engine) or the declared dependencies ever imports the OLD v1 play-engine modules — this has bitten the project twice before and is checked on every phase.

### `resolve()`'s shape (the single most important function in the app)

Roughly: validate/normalize the Draft → resolve species/background/race → compute final ability scores (base + species bonuses + any Half-Elf-style ability choice + ASI progression, threaded per-class in array order) → **loop over every class in `draft.classes`** building each one's own choice templates (features, ASI, spell choices — reusing the same per-class helper functions Phase 3a built, now called once per class instead of once total) → apply background/species/equipment choice templates → resolve every choice against the Draft's submitted selections (with deduplication) → compute `derived` stats (prof bonus from TOTAL character level, HP via `hit_point_max_multiclass` which correctly applies "only your very first class's level 1 ever takes the max hit die") → assemble `sheet` (with `sheet["classes"]` as a list, one entry per class, `sheet["spells"]` as a list, one entry per resolved caster).

An `alias block` pattern is used throughout: a `primary`/`cls`/`cls_id` etc. alias always points at `resolved_classes[0]` for the (still-single-computation) parts of the pipeline — background/species resolution, starting equipment (never multiclassed), saving-throw proficiencies (RAW: primary-class-only).

### Multiclass spellcasting (`derived.spellSlots`/`warlockSpellSlots`, per-caster DC/attack)

Spell slots are tracked in the Resolution for the first time as of Phase 3b-ii (they weren't exposed anywhere before, not even for a single-class caster). The rule (not just the data) matters here and was the source of two real bugs during this phase, both fixed and re-verified — worth restating precisely for anyone touching this code:

- Per RAW (PHB 164), the shared "Multiclass Spellcaster" slot table only applies when a character has **more than one** class that actually grants spell slots **at its current level**. With exactly one slot-granting class, that class's own real single-class table applies directly — NOT a round-down combined-level lookup. `server/engine/resolve.py` counts `slot_granting_entries` by calling `spells_mod.single_class_spell_slots(catalog, cls_id, level)` per class (an ACTUAL grant check, not a class-id-set membership check) and branches accordingly. Getting this wrong (checking class-id set membership instead of an actual current-level grant) silently undercounts slots for a level-1 half caster (Paladin/Ranger) paired with anything — caught twice during this phase's own review process.
- The shared multiclass table itself needs no hardcoded data — it is number-for-number identical to any full caster's own single-class slot progression at the same level, so it's looked up via `catalog.class_level_row("wizard", combined_level)` (Wizard is an arbitrary anchor, not required to be present in the character).
- Warlock's Pact Magic is entirely separate — excluded from the shared pool and combined-level calculation, exposed via its own `derived.warlockSpellSlots`, looked up at Warlock's own class level (never the combined level).
- `spellSaveDC`/`spellAttackBonus` are per-caster values living inside each entry of `sheet.spells` (one entry per resolved caster) — not top-level `derived` scalars (that was the pre-3b-ii shape, primary-class-only, removed as a breaking change).

## Frontend layout (`frontend/src/`)

- `App.tsx` mounts `CatalogProvider` (shared `/api/catalog` fetch, hoisted so 3 pages don't each fetch it separately) wrapping `ResolutionProvider` (calls `/api/resolve` on every Draft change) wrapping `DraftProvider` (the `useReducer`-based Draft state, persisted to `localStorage`) wrapping the routed pages.
- `DraftContext.tsx` — the reducer. Every mutation is a plain action (`SET_NAME`, `SET_CLASS`/`ADD_CLASS`/`REMOVE_CLASS`, `SET_CLASS_LEVEL`/`SET_SUBCLASS`/`SET_HP_ROLL` (all now `classId`-scoped since multiclassing), `SET_ABILITY_METHOD`/`SET_ABILITY_SCORE`, `SET_DETAIL`, `SET_CHOICE_SELECTION`, equipment actions, preferences actions).
- Pages: `HomePage` (name + preferences), `ClassPage` (one "class block" per selected class + "+ Add Another Class", per Phase 3b-i), `BackgroundPage`, `SpeciesPage`, `AbilitiesPage`, `EquipmentPage`, `ExportPage`.
- `types.ts` — hand-written TypeScript types mirroring the backend's actual `Resolution`/`Draft`/`Sheet`/`Derived` shapes (kept manually in sync, not code-generated — this has been a recurring source of "stale type" bugs across phases, since nothing enforces the mirror).
- No test framework configured for the frontend. Verification is `npm run build` (`tsc -b && vite build`) plus manual/browser verification for anything UI-behavioral.

## Known gaps / things a fresh reader should NOT assume are bugs

- Frontend `types.ts` types are hand-maintained, not generated — they periodically drift from the real backend shape until a review catches it (this has happened and been fixed multiple times; there's no structural guard against it happening again).
- No automated frontend test suite exists — all frontend verification is `tsc` type-checking plus manual/browser checks.
- The `_class_label()` string-formatting helper is intentionally duplicated (not shared) between `markdown_export.py` and `pdf_export.py`, matching this project's established convention of these two files mirroring each other's content-selection logic independently rather than sharing a common renderer.
- `sheet.proficiencies` gained `armor`/`weapons`/`tools` fields in Phase 3b-i; `markdown_export.py`/`pdf_export.py` do not yet render them (only `export.py`'s YAML dump surfaces them, since it passes the sheet through wholesale) — a known, small gap, not yet closed.
- A secondary (non-primary) class still shows its own level-1 proficiency-CHOICE card if that class has no `multi_classing.proficiency_choices` of its own — RAW says it should grant nothing when taken as a second class. Known, not yet fixed (flagged during Phase 3b-i's final review, not blocking since the fixed-grant path is already correctly gated).
- **Slot-selection logic is split across `server/engine/resolve.py` (the branch deciding single-class-table vs. combined-table) and `server/engine/spells.py` (the actual lookups)** — Phase 3b-ii's final review flagged this as the most likely friction point for future spell-related work; consolidating into one `spell_slots_for()` function in `spells.py` was recommended but not yet done.
- **`Resolution.pruned` doesn't detect count-shrink staleness** — a spellcaster leveling down with more spells selected than the lower level now allows currently produces a blocking `over-selected-*` problem (pre-existing, unrelated to Phase 3c), not a `pruned` entry. This was Phase 3c's own design spec's ORIGINAL motivating example before its final review found the example didn't match what got built — the spec was corrected, and this gap was spun off as its own follow-up (not yet started).

## Process notes for whoever picks this up

This project has followed a strict "subagent-driven development" workflow the whole way: brainstorm → design spec (committed to `main`) → implementation plan (`docs/superpowers/plans/`, on a feature branch) → per-task implementer/reviewer dispatch loop → final whole-branch review → merge. Every plan's tasks are grounded in direct empirical inspection of the real bundled SRD JSON before being written — this has repeatedly caught planning errors (wrong assumptions about which classes have which data shapes) that would otherwise have become code bugs.

**A sharper version of this lesson emerged from Phase 3b-ii specifically, worth stating precisely for future phases:** the "verify against real SRD data" discipline verifies DATA — are these the right numbers for this level? — but the bundled JSON does not encode multiclassing RULES — which table applies, and when? Phase 3b-ii's plan/design spec got a RAW rule wrong (applying the combined-caster-level round-down table even when only one class actually grants spell slots) DESPITE every number in the spec being individually verified against real Wizard data — because no amount of data verification can catch a rule-selection error; the data was never wrong, the CHOICE of which data to look up was wrong. This bug recurred in two different forms across the phase's fix rounds (once for "does this class count as slot-granting at all," once more precisely for "does it grant slots at its CURRENT level") before being fully closed. **Recommendation for any future phase that implements a RAW rule (not just RAW data): the design spec should quote the governing rule text verbatim and enumerate the cases it distinguishes as an explicit test matrix, kept visibly separate from the data-verification step** — so "which table/branch applies" gets the same scrutiny as "what number does the table return."

Phase 3b-i's own final review flagged a related, more general discipline: plans that ship copy-paste-ready code snippets tend to convert every planning error into an implementation defect plus a review cycle, whereas plans that specify the INVARIANT and let the implementer write the code (and verify against real data) fare better.

**Phase 4a added two more lessons, both from real findings, not hypotheticals:**

1. **A per-task review can find a bug that predates the whole plan, not just the task.** Twice in this phase (Task 3→3b, Task 4→4b), a task's own review — checking the task's NEW tests against `resolve.py`'s EXISTING behavior — found that a downstream consumer (race-trait proficiency forwarding) had never worked correctly, for ANY race, since the feature's original implementation in an earlier phase. Neither gap was reachable by any test written before this phase, because nothing before this phase had a reason to write a test asserting a race's trait-granted weapon/tool proficiency actually reached the sheet. **When a review finds a bug like this, don't just patch it inline — treat it as its own task** (a plan addendum, in this case "Task 3b"/"Task 4b"), get it through the same brief → implement → review → fix-loop discipline as everything else, and update the ledger to say explicitly that the fix is pre-existing-bug cleanup, not new-feature work — this keeps the audit trail honest about what shipped when.

2. **Per-task review cannot see cross-task interactions; only the final whole-branch review can.** The final review for this phase found a genuine data-integrity bug that emerged ONLY from combining Task 5/6's race+subrace-independent merge functions with Task 7's source-filtering (a source-filtered race could leave `sheet.species = None` while its still-persisted subrace independently populated `innateSpells`/`damageModifiers`). Both tasks individually reviewed clean — Task 5/6's reviewer had no reason to think about source filtering (Task 7 didn't exist yet); Task 7's reviewer tested the filter in isolation, without a subrace in play. **This is exactly what the final whole-branch review step is FOR, and skipping it (or treating it as a formality once every per-task review passed) would have shipped this.** Budget real time/effort for it, especially on a plan that grew task-by-task via findings, since each added task increases the surface for this kind of interaction.
