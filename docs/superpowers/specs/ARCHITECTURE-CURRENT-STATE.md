## What this app is

A from-scratch rebuild of a D&D 5e (2014/SRD 5.1 ruleset) character-creator web app. Separate repo from an earlier "v1" (a different, older character builder in a sibling repo, `dnd-app-bg` — not this one). Python/Flask backend, React/TypeScript (Vite) frontend, no database — the character being built lives entirely in the browser's `localStorage` as a JSON "Draft," and the server is a pure, stateless function: `POST /api/resolve` takes a Draft, returns a fully-computed "Resolution" (derived stats, resolved choices, problems, warnings). Every screen re-POSTs the whole Draft and re-renders from the fresh Resolution — there is no incremental/patch API.

## Core data flow

```
Draft (JSON, in browser localStorage)
  → POST /api/resolve
  → resolve(draft, catalog) in server/engine/resolve.py
  → Resolution: { sheet, choices, derived, problems, warnings, pruned }
  → rendered by the frontend, or fed into an export renderer
```

- **`Draft`** (`frontend/src/types.ts`): what the player has chosen so far. Includes `name`, `sources`, `preferences` (hitPointType/usePrerequisites), `classes: ClassSelection[]` (now a real array — see Multiclassing below), `background`, `species`, `abilities`, `equipment`, `details`.
- **`Resolution`**: `sheet` (the finished character — name/level/classes/background/species/abilities/proficiencies/equipment/spells/details), `choices` (every pending-or-resolved Choice, generic across every source), `derived` (ability modifiers, prof bonus, HP, AC, saves, skills, passive perception, `spellSlots`/`warlockSpellSlots` — see Multiclass Spellcasting below), `problems` (blocking issues — e.g. unknown class, over-selected choice), `warnings` (non-blocking — e.g. an equipment envelope that couldn't be represented), `pruned` (as of Phase 3c: one entry per selection that's still sitting in the Draft but no longer reachable — e.g. an ASI tied to a level the player leveled back down from, or a feature choice tied to a subclass the player cleared — see "Pruning" below; also populated, for spellcaster cantrip/known-spell choices only, when the id survives but the allowed count shrinks or options fall out of range).
- **The generic Choice model**: every player decision — a class skill pick, a spell choice, an ASI, starting equipment — is represented the same way: `{id, source, label, description, count, options, selected, status}`. `resolve()` builds a `choice_templates` list from every source (class/background/species/equipment/ASI/spells), then applies whatever the Draft already submitted to produce the final `choices` list. The frontend's `<ChoiceCard>`/`<ChoicePicker>` components render ANY choice generically — new choice-producing features (like multiclass proficiency choices) need zero new frontend rendering code, only a new template-building function on the backend.

## Where the rules data comes from

`server/catalog/loader.py` loads the bundled SRD JSON (`chargen/data/srd/*.json` — the SAME data files the OLD "v1" `chargen` module uses, ported verbatim in Phase 1, never modified) into a `Catalog` dataclass: `classes`, `levels`, `features`, `subclasses`, `races`, `subraces`, `traits`, `backgrounds`, `items`, `spells` — each indexed by its SRD `index` field. As of Phase 4a, `races`/`subraces`/`traits` are ADDITIVELY merged with data from official sourcebooks (see "Sourcebook data (Phase 4a)" below) — everything else (`classes`, `backgrounds`, `items`, `spells`, etc.) is still SRD-only; no 5etools adapter exists for those yet, and no 2024-ruleset content has been imported (XPHB races import as just another labeled source, not a separate ruleset switchboard).

Where the bundled SRD data doesn't structurally carry an answer the engine needs (e.g. which ability governs which skill, which classes are half-casters), `server/catalog/reference_data.py` hardcodes it as an open 5e RAW fact, always with a comment explaining why it couldn't be read from the data.

## Sourcebook data (Phase 4a)

As of Phase 4a, ~160 races and ~92 usable subraces from official D&D sourcebooks (Volo's, Xanathar's, Mordenkainen's, Tasha's, Eberron, and ~15 more) are selectable alongside the 9 bundled SRD races, with full mechanical fidelity: ability bonuses (fixed, choice, and a "choose N of any skill/tool" wildcard), skill/tool/weapon/armor proficiencies (fixed grants and player choices), damage resistances/immunities/vulnerabilities, condition immunities, and innate spellcasting (93/102 real innate-spell references resolve against the bundled SRD spell list; the rest degrade gracefully — spell name shown, `spellId: null` — since this app hasn't imported non-SRD spell data).

**Where the raw data lives:** a separate v1 tool (`chargen/sync.py --official`, not part of this app's own code, ported verbatim from an earlier project) fetches `races.json`/`backgrounds.json` from `5etools-mirror-3/5etools-src` (MIT-licensed) into `chargen.sources.official_dir()` — by default `~/.claude/dnd/.data/official/`, deliberately OUTSIDE this repo, never committed, and respecting `DND_CAMPAIGN_ROOT`. `chargen.sources.has_official()` checks whether it's been fetched on a given machine. **This is a real prerequisite a fresh environment won't have by default** — without running that sync command once, `catalog.races` contains only the 9 bundled SRD races, and every sourcebook-race test in the suite is `skipif`-gated on `has_official()` and silently skips.

**The new module:** `server/catalog/official_source.py` (~800 lines) converts the raw 5etools-shaped JSON into the EXACT same dict shape `catalog/loader.py` already produces for SRD races/subraces/traits — so `catalog/choices.py` and `engine/resolve.py` need zero changes to CONSUME sourcebook races (they already read "the SRD shape" generically). This module is also the SINGLE place in the entire codebase allowed to `import chargen.sources` directly — `chargen` lives at the repo root, a sibling of `server/`, and every real way this app runs (`cd server && python app.py`, `cd server && pytest`) has `server/` as its working directory, which does NOT put the repo root on `sys.path`; `official_source.py` patches `sys.path` at import time and re-exports `official_dir`/`has_official`/`load_official_races`, and every other file (including every test) imports those three names from `catalog.official_source`, never from `chargen.sources` directly. A stray direct import elsewhere is a real, reproducible `ModuleNotFoundError`, not a style nit.

Each sourcebook record's id is source-qualified (e.g. `aasimar-vgm`, `aasimar-mpmm`, `aasimar-xphb` — the same monster/race can be reprinted across multiple books, each a genuinely distinct record) — SRD ids have no such suffix, so collision is structurally impossible. `_copy`/`_mod`-based 5etools records (their own "defined as another record plus a diff" shorthand) are skipped entirely, a disclosed, bounded cut.

**`Draft.sources: string[]`** (existed since Phase 0, never read until Phase 4a) now filters which races are selectable: non-empty means only races whose `source` is in the list (plus SRD, always available) resolve; empty/absent means everything is available. **The real frontend default is `[]`** (`frontend/src/DraftContext.tsx`'s `emptyDraft.sources`) — it was briefly `["srd"]` during this phase's own review (a stale Phase-0 placeholder that would have silently made every sourcebook race unselectable the moment this shipped, caught and fixed before merge). Since Slice 10 the filter also covers subspecies (each carries its own `source`) and `GET /api/catalog?sources=` hides filtered-out records in the pickers; Home has a Sources picker (see "Slice 10" at the end).

**Two real, pre-existing bugs surfaced and fixed during this phase** (not introduced by it — both affected bundled SRD races since the app's inception, only ever caught because this phase's own new tests happened to exercise a code path nothing had tested before): `engine/resolve.py`'s trait-proficiency scanning only ever forwarded `skill-` prefixed ids from race/subrace traits into the sheet — tool/weapon/armor grants (e.g. SRD Dwarf's own "Dwarven Combat Training") and race-sourced proficiency CHOICES (e.g. SRD Half-Elf's own "Skill Versatility") never reached `sheet.proficiencies`, for any race, ever, until fixed. Both fixes reuse existing machinery (`_categorize_proficiency`, `build_choice_template`) with small, targeted additions — see `server/engine/resolve.py` directly for the current shape, not this doc, since it will drift.

**New `sheet` fields added this phase, currently with NO frontend consumer** (backend-only, visible via raw `/api/resolve` JSON, not yet rendered anywhere a player sees, and not yet in `markdown_export.py`/`pdf_export.py`): `sheet.damageModifiers: {resistances, immunities, vulnerabilities}`, `sheet.conditionImmunities`, `sheet.innateSpells`.

Phase 4a deliberately did NOT touch: classes/subclasses/spells/equipment-items from other sourcebooks (v1 never built normalizers for these either — a future phase's own scope); backgrounds (Phase 4b, now complete — see below); Feats as a mechanic (Phase 4c, not yet started, deliberately deferred until 4b's shape revealed how feat-references should be structured — it now has, see below); a distinct 2014-vs-2024 ruleset toggle; subrace-level source filtering (only the parent race's source is checked — a subrace from an unlisted book is still reachable today if its parent race's book is listed, a disclosed, narrow gap).

## Sourcebook data (Phase 4b)

Directly extends Phase 4a's architecture — `server/catalog/official_source.py` (now ~1550 lines, races AND backgrounds) gained `load_official_backgrounds()`, following the exact same pattern: converts raw 5etools background JSON into the SRD dict shape `catalog/loader.py` already produces for the bundled Acolyte background, merged additively at load time. `official_source.py` remains the SINGLE place in the codebase allowed to `import chargen.sources` directly — this constraint held across the whole phase (independently re-verified by the final whole-branch review). Backgrounds are structurally simpler than races here: SRD backgrounds carry proficiencies/languages/equipment as direct top-level dict fields, not indirected through a separate "traits" catalog, so no synthetic-trait-minting step was needed.

**What's covered, full fidelity:** skill/tool proficiencies (fixed grants and player choices, including an "any N" wildcard reusing Phase 4a's `any_skill`/`any_tool` machinery unmodified), fixed and choice language grants (the wildcard case reuses SRD's own pre-existing `language_options`/`resource_list` mechanism verbatim — zero new code), the real 2024 background ability-score-improvement rule (every one of 60 real records offers the SAME universal choice — "+2/+1 split between two of a named 3-ability pool" or "+1 to all three," 7 selectable options total, not a per-background varying mechanic — verified exhaustively), the starting-equipment "choose package A or B" shape (reusing the existing `"multiple"` option-bundling mechanism), starting gold (both a fixed `starting_gold` field — which, it turned out, had NEVER been read by this app for ANY background including bundled SRD, an old gap predating this whole plan — and gold from a selected equipment bundle), non-catalog ("narrative") equipment items no longer silently dropped, and inert feat storage (`sheet.grantedFeats` — pure data pass-through, explicitly no prerequisite checking or effect application, deferred to a future Phase 4c).

**Explicitly out of scope, disclosed:** the `additionalSpells` field's `"expanded"` key (a spell-LIST-EXPANSION mechanic — "these spells count as being on your class's list" — genuinely different from races' `"innate"` spellcasting; nothing in this engine models it); a full narrative-item catalog/registration system (non-catalog equipment items are shown as text, never resolved into real inventory entries); House Agent/ERLW's narrative-context-dependent tool choice (12 dragonmarked-house alternatives, always resolves to the first one, disclosed in a docstring rather than solved); sub-1-gp coinage (a fixed grant of, say, 1 silver piece is simply not tracked — `starting_gold` stays `None` rather than reporting a wrong `0`).

**Process pattern that repeated three times this phase, worth knowing if you're the next reader:** a task's own review found a real, PRE-EXISTING bug in `resolve()`'s consumption of background data (not introduced by that task, only newly surfaced by its own tests) — Task 1 → Task 1b (tool/weapon/armor proficiency grants never reached the sheet, mirroring Phase 4a's Task 3→3b for races), Task 2 → Task 2b (an independent reviewer FORCED a commit split when an implementer fixed a similarly-discovered wiring gap inline instead of disclosing it — this plan's controller had to actually split one bundled commit into two after the fact to preserve the established process), Task 5 → Task 5b (a near-universal, 75/76-real-backgrounds-affected bug where selected gold/flavor/category bundle members were silently dropped, PLUS the starting_gold gap above). The FINAL whole-branch review then found a fourth, larger instance the per-task process couldn't reach at all — fixed equipment/gold for the majority (2014-era) `"_"`-keyed background shape had never been wired up by ANY task (each task's own scope genuinely didn't include it, so no per-task review had reason to look) — closed as part of the final review's own authorized fix wave, which itself introduced and then closed one small regression (a fabricated `0 gp` for two sub-1-gp records) before merge.

## Sourcebook data (Phase 4c-i)

The FIRST slice of feats as a real mechanic — Phase 4b's `sheet.grantedFeats` (inert since it was built) now actually applies its feats' effects. `server/catalog/official_source.py` (now ~2100 lines, races+backgrounds+feats — a split into submodules is recommended, not yet done) gained `load_official_feats()`, following the exact same pattern as races/backgrounds — EXCEPT there is no bundled SRD feats file at all (2014 SRD has no feats mechanic), so `Catalog.feats` is populated ONLY from official data, with no SRD merge step. `resolve()` had ZERO prior consumption of `catalog.feats` before this phase — a new `_resolve_granted_feats(ids, catalog, refs)` function (in `engine/resolve.py`) is the first-ever bridge from a background's granted-feat slugs to actual `catalog.feats` entries, positioned EARLY in `resolve()` (before the ability-score pass and the proficiency merge block) so feat-granted effects can feed the same merge points species/background already feed.

**What's covered, full fidelity:** ability bonuses (fixed and choice, reusing/generalizing Phase 4a/4b's machinery — this also HARDENED a SHARED helper, `_ability_bonuses_from_5etools`, against feat-only extra keys like `"hidden"`/`"max"` that races/backgrounds never carry, verified behavior-preserving for the existing race/background path via a direct old-vs-new comparison across all 74 real race entries), skill/tool/weapon/armor proficiencies (fixed and choice, reusing Phase 4a/4b's machinery), languages (fixed and choice, reusing Phase 4b's machinery, plus a fix for a real Phase-4b-inherited slug bug — a `;`-suffixed spell-list-restricted feat name variant was embedding the literal `;` into its slug, silently breaking any match), damage resistances/immunities/condition-immunities (additively merged into the SAME `sheet.damageModifiers`/`conditionImmunities` fields races already populate — a feat's resistance ADDS to a race's, never replaces it), a NEW `sheet.senses` field (feat-only for now — 0/160 races carry any senses data — "higher range wins" for same-type sources, confirmed real 5e RAW), a NEW `sheet.expertiseSkills` field, saving-throw proficiencies (added to `proficient_save_abilities`, previously class-only), and structured prerequisite checking (character level, minimum ability score — mirroring the existing `_multiclass_prerequisite_problems` pattern exactly, gated on a new `preferences.usePrerequisites.feats` toggle sibling to the existing `.multiclass` key — both are independent sibling keys on one shared preferences dict, NOT one shared toggle).

**A pre-existing bug fixed as part of this phase's own final-review fix wave, affecting how MANY real background→feat grants even resolve at all:** Phase 4b's own feat-grant conversion stripped the `|source` suffix off a background's raw feat-grant key before slugging, so when a bare slug matched feats in MORE than one source (9 real slugs do — e.g. "Alert" exists in both PHB and XPHB), the resolver had no way to disambiguate and silently skipped the grant — even though the source was right there in the raw data the whole time. This affected 28 of 70 real background→feat grants, including nearly every core 2024 background (Sailor, Soldier, Acolyte, Charlatan, and more). Fixed by emitting a parallel source-qualified `feat_refs` list alongside the existing bare `feats` list, tried first before falling back to the pre-existing ambiguity logic.

**Explicitly, deliberately out of scope for this slice** (per the design spec — a much larger, separate undertaking each): `additionalSpells` in any of feats' 16 distinct shape combinations (more heterogeneous than either races' or backgrounds' own spell shapes — includes a query-filter spell selector like `"level=1|class=Sorcerer"`, not a literal spell name, that this engine has no precedent for resolving); the "take a feat instead of a normal class-level ASI" mechanic (feats are NOT yet player-selectable outside a background's fixed grant — this is the natural next slice, Phase 4c-ii); `repeatable`/`repeatableHidden` feat multiplicity; `exclusiveFeatCategory` prerequisite enforcement (e.g. "no other Dragonmark feat"); a feat's non-structured prerequisites (campaign, other-feat-required, feature-name, free text — only `level`/`ability` are checked; everything else is disclosed but never enforced); `skillToolLanguageProficiencies`'s "2 of any combination" shape (the same open question Phase 4b left for backgrounds, now confirmed on 2 feats too, still unresolved); choice-shaped feat effects being converted into the catalog but never offered as an actual selectable Choice — **this gap is now CLOSED, see "Sourcebook data (Phase 4c-ii)" below** (was disclosed here as out of scope for this phase, closed the same day by the next phase).

**Process notes specific to this phase:** the plan executed with NO chained-gap follow-up tasks needed mid-plan (unlike Phase 4a's 7→9 and Phase 4b's 6→9 task growth) — but its OWN Task 5 discovered the "resolve() never consumed catalog.feats at all" gap and had to build the first resolution bridge itself, and its own Task 6 had to resolve three things Task 5's review flagged (the slug/source bug above, a call-site hoist, and de-duplicating slug-generation logic into one shared, promoted `slug()` function used by races/backgrounds/feats alike). The FINAL whole-branch review then found the slug/source bug was itself incomplete (Phase 4b's OWN grant-key parsing, not just Task 5/6's new resolution code, was the root cause) plus a latent "a feat's own bonus can satisfy its own prerequisite" ordering bug (harmless today, would matter the moment Phase 4c-ii ships) plus the choice-shaped-effects gap above — all three resolved in the final review's own authorized fix wave. **Lesson for whoever picks up Phase 4c-ii**: this phase's per-task reviews were unusually good at catching gaps in code THIS phase itself just wrote, but the deepest bug (the source-stripping in Phase 4b's grant-key parser) had been sitting in ALREADY-MERGED code for a whole prior phase, invisible until this phase's own resolution logic gave it something to actually break — the same "a later phase's tests are what finally exercise an earlier phase's dormant bug" pattern Phase 4a/4b already established, now confirmed a third time.

## Sourcebook data (Phase 4c-ii)

The SECOND slice of feats as a mechanic, deliberately small and bounded (the first of two user-approved slices — the larger, separate "ASI-or-feat" player-selectable-feat mechanic is next). Closes the exact gap Phase 4c-i's own final review disclosed and left open: a background-granted feat's `ability_bonus_options`/`proficiency_choices`/`language_options` were already converted into the catalog, but `resolve()` never turned any of them into a real, selectable `Choice` — so a background whose granted feat had ONLY choice-shaped content gave the player nothing.

**Architecture — no new mechanism, purely additive participation in the existing one.** A new `_feat_choice_templates(feats)` in `server/engine/resolve.py` mirrors the pre-existing `_background_choice_templates`/`_species_choice_templates` pattern exactly for a feat's `proficiency_choices` and `language_options` fields (same `build_choice_template` call, same `":proficiency-choice"` cid-substring convention the merge sites key off). A SEPARATE, early-called `_feat_ability_bonus_choice_templates`/`_feat_ability_bonus_deltas` pair handles `ability_bonus_options` — this had to be its own thing, not folded into `_feat_choice_templates`, because ability bonuses must be resolved BEFORE `final_scores` is computed (mirroring the reason background's OWN ability-bonus choice already lives in a separate early pass, not inside `_background_choice_templates`) — the implementation plan's own text assumed the wrong precedent here (said to mirror `_background_choice_templates`'s "ability-bonus block," which never existed), and the implementer correctly deviated from the plan's literal wording once the real architecture became clear; the final review independently verified this deviation was the right call before merge. Three pre-existing merge sites (the ones already extended for `"species"`/`"background"` — the `proficient_skills` merge, the `_categorize_proficiency` elif chain, the language-grant merge) gained a fourth `"feat"` source kind; the ability-bonus path needs no merge site of its own, since its early pass writes deltas directly into `feat_bonuses`, summed into `final_scores` alongside species'/background's own bonuses.

**Real-data coverage is asymmetric, disclosed.** Exactly one real background→feat combination reaches the `proficiency_choices` path with full end-to-end test coverage: Artisan/XPHB → Crafter/XPHB ("choose 3 of 8 artisan's tools"). A live sweep of all 136 real backgrounds during the final review found 5 real backgrounds now produce a genuine feat-sourced Choice: artisan-xphb, entertainer-xphb, harper-frhof, mythalkeeper-frhof, purple-dragon-squire-frhof (the last two weren't named in the original design spec — found empirically). Zero real background→feat grants reach `ability_bonus_options` or `language_options` — both of those two paths are tested via a synthetic feat only, clearly labeled as such in the test comments, not presented as real coverage.

**A real regression found by the final whole-branch review, not by either per-task review (a genuine cross-layer gap neither task-scoped lens could see alone):** the new `"feat"`-kind choices were invisible in the frontend (`BackgroundPage.tsx` only ever rendered `kind === "background"`, `ChoiceSourceKind` in `types.ts` had no `"feat"` value) while BOTH export gates (`server/app.py`'s `_pending_export_problems`, `frontend/src/pages/ExportPage.tsx`'s `canExport`) block export on ANY pending choice regardless of kind — meaning the 5 real backgrounds above went from "silently gets nothing from its feat" (the pre-4c-ii state) to "permanently unexportable in the shipped UI" (worse). Fixed in the same branch's authorized fix wave: `"feat"` added to `ChoiceSourceKind`, `BackgroundPage.tsx` now renders `kind === "background" || kind === "feat"`, `StepNav.tsx`'s Background badge counts both. No backend change was needed — `SET_CHOICE_SELECTION` already hardcodes `source: "background"` for every choice `BackgroundPage` renders, and `resolve()` already reads feat selections from that same `draft.background.choices` dict.

**Both items flagged here as deferred to the next slice are now CLOSED — see "The ASI-or-feat mechanic" below.**

## The ASI-or-feat mechanic

The second, larger of the two user-approved slices (2026-09-28: "do the small one, then immediately the big one"). At any class level that grants an Ability Score Improvement (levels 4/8/12/16/19 for most classes, plus Fighter's extra 6/14 and Rogue's extra 10 — `_asi_granting_levels`, unchanged since Phase 3a), the player may now take a feat INSTEAD of the ability-score increase — the base PHB/XPHB rule, not a variant.

**Architecture — one merged Choice, no new mechanism.** `_asi_choice_templates` (Phase 3a, unchanged cid `class:{cls_id}:{lvl}:asi`, unchanged `source.kind: "class"`) had its `options` list extended: the existing 21 ability-combo options (6 single-ability "+2" plus the 15 two-ability "+1/+1" pairs — NOT 7, a miscount in the original design/plan text, corrected during implementation) PLUS one option per real "General"-category feat (94 — the real 95 minus the literal "Ability Score Improvement"/XPHB catalog entry itself, which is the 2024-rules' own representation of the same classic combo mechanic and would otherwise duplicate it under a second label), each option disabled with a reason when its prerequisite isn't met (reusing Phase 4c-i's `_feat_structured_prerequisite`/`_feat_prerequisite_alt_met` unchanged) and filtered by `draft.sources` (reusing the exact existing race/background source-filter pattern — 2014 SRD has zero feats, so an SRD-only draft correctly offers none). **This needed zero frontend change for the top-level choice** — `ClassPage.tsx`'s existing cid-prefix filter already matched it.

A new pre-pass, `_resolve_asi_selected_feats(resolved_classes, catalog)`, runs alongside the existing `_resolve_granted_feats` (background) call and resolves any feat a class's `class_choices` dict currently names at one of its own ASI levels, tagging each with its origin (`class:{cls_id}:{lvl}:asi:feat:{index}`, stashed as `feat["_asi_origin"]`/`feat["_asi_level"]`). `_feat_choice_templates`/`_feat_ability_bonus_choice_templates` (Phase 4c-ii) each gained an optional `origin` parameter — when given, a feat's cascaded sub-choice cids scope under that class-ASI-specific prefix instead of the background-only default `feat:{index}:...`, closing the cid-collision gap Phase 4c-ii's own final review had flagged and deferred. `_apply_asi_progression` (Phase 3a) gained a `feat_deltas_by_cid` parameter so a selected feat's ability-bonus delta (fixed + any already-chosen sub-choice) is applied at the correct point in the per-level walk, feeding later levels' cap checks correctly.

**A feat pick with an unmet prerequisite is gated exactly like an over-cap ASI combo — it does NOT apply, matching the Choice-model's own existing "disabled option never applies" precedent**, not the "report a problem but still grant it" policy background grants use (background grants have no per-level gate to hook this into; ASI picks do, so they get the stricter, more correct treatment). A feat's ability-bonus delta is capped at the 20-point ability-score ceiling the same way (reusing `asi_mod.asi_exceeds_cap`) — matching real 2024 feat text ("to a maximum of 20"), closing a gap that was always latent in the background-feat path too but rarely reachable there. `_feat_prerequisite_problems` (Phase 4c-i/4c-ii) now also subtracts a feat's own CHOSEN ability-bonus delta — not just its fixed one — before checking that SAME feat's own prerequisite, but **only for background-granted feats**: an ASI-selected feat's own prerequisite is already checked at that level's own running scores with its own delta excluded by construction (the gate above), so re-subtracting it a second time here would be either redundant or, when a delta was cap-skipped, actively wrong — this was built, found to be a real latent bug by the final review (not a harmless no-op), and removed before merge.

**Real-data coverage, confirmed this phase**: Skill Expert/XPHB is the primary real end-to-end case — it carries BOTH a genuine proficiency choice (`skillProficiencies: [{"any": 1}]`) and a genuine ability-bonus choice on the same feat, fully exercised. 10 real General feats combine an ability-score prerequisite with a choice-shaped ability bonus (Athlete, Charger, Dual Wielder, Grappler, Inspiring Leader, Observant, Polearm Master, Ritual Caster, Sentinel, Speedy) — the concrete real cases the self-bonus-prerequisite fix closes. 17 real General feats have a structured (level/ability) prerequisite at all; the rest (feat/spellcasting/proficiency/featCategory prerequisites, 59 of 95) stay disclosed-but-unenforced, the SAME pre-existing policy Phase 4c-i already established for background-granted feats, not a new gap this slice introduces.

**A real cross-layer regression this branch's own changes exposed in the adjacent, already-merged Phase 4c-ii code (caught by this branch's own task review, not the final review this time):** `ClassPage.tsx`'s filter needed widening to `(kind === "class" || kind === "feat")` so a feat's cascaded sub-choices actually render — but Phase 4c-ii's `BackgroundPage.tsx`/`StepNav.tsx` filters were kind-only with NO cid-prefix scoping, so they started ALSO matching ASI-selected feats' cascaded choices (same `"feat"` kind, now also reachable with a `class:`-prefixed cid) — causing the same choice to render on BOTH /class and /background and double-count on both nav badges. Fixed by scoping both pages' filters to their own cid-prefix (`ClassPage`: requires `class:{classId}:`; `BackgroundPage`: excludes any `class:`-prefixed cid) — verified in both directions (an ASI pick no longer leaks to /background; a background-granted feat's own cascaded choice, e.g. Artisan/XPHB → Crafter/XPHB, still renders correctly there).

**A second, final-review-only finding, also fixed before merge:** a feat's cascaded sub-choice cards (built by `_feat_choice_templates`/`_feat_ability_bonus_choice_templates`) rendered with bare, generic labels ("Skill Proficiency", "Ability Score Increase") and no feat-name or level context — genuinely ambiguous with two or more feat picks. Fixed by prefixing every such label with the feat's own name (e.g. "Skill Expert: Ability Score Increase"), applied to BOTH the background-granted and ASI-origin paths, plus setting `source.level` for the ASI-origin path specifically (picked up for free by `ChoiceCard.tsx`'s existing `source.level != null` display).

**Explicitly, deliberately NOT fixed, disclosed instead (per the final review's own judgment — none block real use today):**
- Skill Expert's expertise-skill pick and Resilient's saving-throw-proficiency pick both silently collapse to `[]` (`official_source.py`'s `_expertise_skills_from_5etools`/`_saving_throw_proficiencies_from_5etools` only convert FIXED entries, never the choice-shaped `anyProficientSkill`/`{"choose":...}` portion) — a pre-existing Phase 4c-i catalog-layer gap, but now directly, prominently reachable via a free ASI-level pick rather than an obscure background grant. Docstrings corrected and this gap explicitly disclosed; the actual conversion fix is real, separate follow-up work.
- Duplicate problem ids when the SAME feat is blocked (unmet prerequisite) at two different ASI instances — a consequence of the pre-existing "duplicate feats not prevented at all" gap, not new.
- `_feat_prerequisite_problems`'s FIXED-bonus subtraction has the same theoretical "redundant or wrong" pattern for ASI-origin feats the removed chosen-delta plumbing did — unreachable today since all 17 real ability-prereq'd General feats have single-ability deltas only.
- A feat's own ability-bonus sub-choice options aren't individually marked `disabled` when that specific ability is already at 20 — the cap IS correctly enforced when applying, just not explained to the player at the option level.
- With two+ classes each independently able to pick a feat, whether a given pick's prerequisite passes can depend on `draft.classes`' array order (an existing, documented consequence of the per-class sequential ability-score walk, now newly visible for prerequisite checks specifically, not just cap checks) — the UI doesn't let a player reorder classes, so this is low-impact.
- `repeatable`/`repeatableHidden`/`exclusiveFeatCategory` and non-structured prerequisites (feat/spellcasting/proficiency/featCategory) remain disclosed-but-unenforced — unchanged policy from Phase 4c-i.
- `additionalSpells` for feats — now largely covered, see "Feats' additionalSpells (2026-10-08)" below for what is and is not modelled.

### `resolve()`'s shape (the single most important function in the app)

Roughly: validate/normalize the Draft → resolve species/background/race → compute final ability scores (base + species bonuses + any Half-Elf-style ability choice + ASI progression, threaded per-class in array order) → **loop over every class in `draft.classes`** building each one's own choice templates (features, ASI, spell choices — reusing the same per-class helper functions Phase 3a built, now called once per class instead of once total) → apply background/species/equipment choice templates → resolve every choice against the Draft's submitted selections (with deduplication) → compute `derived` stats (prof bonus from TOTAL character level, HP via `hit_point_max_multiclass` which correctly applies "only your very first class's level 1 ever takes the max hit die") → assemble `sheet` (with `sheet["classes"]` as a list, one entry per class, `sheet["spells"]` as a list, one entry per resolved caster).

An `alias block` pattern is used throughout: a `primary`/`cls`/`cls_id` etc. alias always points at `resolved_classes[0]` for the (still-single-computation) parts of the pipeline — background/species resolution, starting equipment (never multiclassed), saving-throw proficiencies (RAW: primary-class-only).

### Multiclass spellcasting (`derived.spellSlots`/`warlockSpellSlots`, per-caster DC/attack)

Spell slots are tracked in the Resolution for the first time as of Phase 3b-ii (they weren't exposed anywhere before, not even for a single-class caster). The rule (not just the data) matters here and was the source of two real bugs during this phase, both fixed and re-verified — worth restating precisely for anyone touching this code:

- Per RAW (PHB 164), the shared "Multiclass Spellcaster" slot table only applies when a character has **more than one** class that actually grants spell slots **at its current level**. With exactly one slot-granting class, that class's own real single-class table applies directly — NOT a round-down combined-level lookup. `server/engine/resolve.py` counts `slot_granting_entries` by calling `spells_mod.single_class_spell_slots(catalog, cls_id, level)` per class (an ACTUAL grant check, not a class-id-set membership check) and branches accordingly. Getting this wrong (checking class-id set membership instead of an actual current-level grant) silently undercounts slots for a level-1 half caster (Paladin/Ranger) paired with anything — caught twice during this phase's own review process.
- The shared multiclass table itself needs no hardcoded data — it is number-for-number identical to any full caster's own single-class slot progression at the same level, so it's looked up via `catalog.class_level_row("wizard", combined_level)` (Wizard is an arbitrary anchor, not required to be present in the character).
- Warlock's Pact Magic is entirely separate — excluded from the shared pool and combined-level calculation, exposed via its own `derived.warlockSpellSlots`, looked up at Warlock's own class level (never the combined level).
- `spellSaveDC`/`spellAttackBonus` are per-caster values living inside each entry of `sheet.spells` (one entry per resolved caster) — not top-level `derived` scalars (that was the pre-3b-ii shape, primary-class-only, removed as a breaking change).

## Process notes for whoever picks this up

This project has followed a strict "subagent-driven development" workflow the whole way: brainstorm → design spec (committed to `main`) → implementation plan (`docs/superpowers/plans/`, on a feature branch) → per-task implementer/reviewer dispatch loop → final whole-branch review → merge. Every plan's tasks are grounded in direct empirical inspection of the real bundled SRD JSON before being written — this has repeatedly caught planning errors (wrong assumptions about which classes have which data shapes) that would otherwise have become code bugs.

**A sharper version of this lesson emerged from Phase 3b-ii specifically, worth stating precisely for future phases:** the "verify against real SRD data" discipline verifies DATA — are these the right numbers for this level? — but the bundled JSON does not encode multiclassing RULES — which table applies, and when? Phase 3b-ii's plan/design spec got a RAW rule wrong (applying the combined-caster-level round-down table even when only one class actually grants spell slots) DESPITE every number in the spec being individually verified against real Wizard data — because no amount of data verification can catch a rule-selection error; the data was never wrong, the CHOICE of which data to look up was wrong. This bug recurred in two different forms across the phase's fix rounds (once for "does this class count as slot-granting at all," once more precisely for "does it grant slots at its CURRENT level") before being fully closed. **Recommendation for any future phase that implements a RAW rule (not just RAW data): the design spec should quote the governing rule text verbatim and enumerate the cases it distinguishes as an explicit test matrix, kept visibly separate from the data-verification step** — so "which table/branch applies" gets the same scrutiny as "what number does the table return."

Phase 3b-i's own final review flagged a related, more general discipline: plans that ship copy-paste-ready code snippets tend to convert every planning error into an implementation defect plus a review cycle, whereas plans that specify the INVARIANT and let the implementer write the code (and verify against real data) fare better.

**Phase 4a added two more lessons, both from real findings, not hypotheticals:**

1. **A per-task review can find a bug that predates the whole plan, not just the task.** Twice in this phase (Task 3→3b, Task 4→4b), a task's own review — checking the task's NEW tests against `resolve.py`'s EXISTING behavior — found that a downstream consumer (race-trait proficiency forwarding) had never worked correctly, for ANY race, since the feature's original implementation in an earlier phase. Neither gap was reachable by any test written before this phase, because nothing before this phase had a reason to write a test asserting a race's trait-granted weapon/tool proficiency actually reached the sheet. **When a review finds a bug like this, don't just patch it inline — treat it as its own task** (a plan addendum, in this case "Task 3b"/"Task 4b"), get it through the same brief → implement → review → fix-loop discipline as everything else, and update the ledger to say explicitly that the fix is pre-existing-bug cleanup, not new-feature work — this keeps the audit trail honest about what shipped when.

2. **Per-task review cannot see cross-task interactions; only the final whole-branch review can.** The final review for this phase found a genuine data-integrity bug that emerged ONLY from combining Task 5/6's race+subrace-independent merge functions with Task 7's source-filtering (a source-filtered race could leave `sheet.species = None` while its still-persisted subrace independently populated `innateSpells`/`damageModifiers`). Both tasks individually reviewed clean — Task 5/6's reviewer had no reason to think about source filtering (Task 7 didn't exist yet); Task 7's reviewer tested the filter in isolation, without a subrace in play. **This is exactly what the final whole-branch review step is FOR, and skipping it (or treating it as a formality once every per-task review passed) would have shipped this.** Budget real time/effort for it, especially on a plan that grew task-by-task via findings, since each added task increases the surface for this kind of interaction.


## Follow-up cleanups after the ASI-or-feat mechanic (2026-10-08)

- **Skill Expert / Resilient choices**: `official_source` now emits `expertise_choices` (from `anyProficientSkill`) and `saving_throw_choices` (from `savingThrowProficiencies.choose`) on each feat; `_feat_choice_templates` turns them into real Choices (cids `...:expertise-choice-{i}` / `...:save-choice-{i}`, deliberately not containing `proficiency-choice`), and `resolve()` merges selections into `sheet.expertiseSkills` and the saving-throw proficiency list. Expertise options are gated to proficient skills by `_gate_expertise_choices` (non-proficient options are disabled with reason "not proficient"; a stale selection is dropped and reported as a non-blocking `pruned` entry, leaving the choice pending). The same change fixed a leak where an Expertise pick also made the character proficient in that skill.
- **Duplicate-feat prevention**: feats carry a `repeatable` flag. A non-repeatable feat already granted by the background or picked at an earlier ASI level (class order, then level — first pick wins) is offered disabled ("already taken"), skipped if still selected, and reported as a `feat-duplicate-{index}-{cid}` problem. `repeatable` feats (e.g. Elemental Adept) are exempt.
- **Export of armor/weapon/tool proficiencies** in Markdown and PDF via `reference_data.proficiency_label`.

## Feat prerequisite enforcement beyond level/ability (2026-10-08)

- **Enforced keys, and where**: at the ASI walk and the ASI option reasons only (`_ASI_GATE_PREREQUISITE_KEYS` in `server/engine/resolve.py`): `level`, `ability`, `feat`, `spellcasting2020`, `feature` (Spellcasting / Pact Magic), `proficiency` (armor light/medium/heavy/shield, weaponGroup martial) and `featCategory`. Both the walk (`_apply_asi_progression`) and the option templates (`_asi_choice_templates`) go through `_feat_prerequisite_unmet_reason`, so they always agree. An unmet option is disabled with "prerequisite not met", plus ": requires ..." when the feat has exactly one alternative. A prerequisite failure wins over "already taken". A hand-edited pick that would be disabled is blocked and reported as `feat-prerequisite-unmet-{index}`. An OR of alternatives is all-or-nothing: if any alternative has a key or value shape this app cannot verify, the whole feat is left unenforced (e.g. Spellfire Adept is enforced since both its alternatives are now verifiable).
- **Background second pass unchanged**: `_feat_prerequisite_problems` keeps the old `_STRUCTURED_FEAT_PREREQUISITE_KEYS = {"level", "ability"}`. Never widen it, or ASI-gated picks would produce false problems there.
- **Held state** (`_HeldFeatState`): the feats the character holds start as the background-granted feats; then each ASI pick that passes the gate is added in walk order (resolved_classes order, then level), so "first pick wins". A feat never satisfies itself, a later pick never satisfies an earlier one, and a blocked pick never chains. Option templates read a per-level snapshot (`held_by_level`), never the live object. Pre-walk inputs: spellcasting (any class with spell slots at its own level, via `single_class_spell_slots`), and FIXED proficiency grants from classes (primary proficiencies for the first class, multiclass proficiencies otherwise), race/subrace traits and the background's starting proficiencies, plus granted-feat proficiencies.
- **Timing simplification (disclosed)**: pre-walk inputs use the FINAL character, the same way `level` uses total_level. This is permissive, never a false disable (e.g. a Paladin 2 multiclassed in at a later level still counts for an earlier Fighter 4 pick).
- **Disclosed gap**: proficiency CHOICE selections (skill/tool/etc. picks) are not available before the walk. A scan of all race, subrace, background, feat and trait `proficiency_choices` found none offering armor, shield or martial-weapon options, so no real data is affected today.
- **Still disclosed-only (never enforced)**: `campaign`; `background` (always satisfied by the granting background); `exclusiveFeatCategory` (only Dragonmark feats, never ASI-eligible); `race`; `other`/`otherSummary`; `spellcasting` (2014) / `spellcastingFeature` (Rune Shaper only); dict-shaped `level` (IoHS, Squire); `repeatableHidden` (display flag; `repeatable` is honoured); `feat_options` (Rewarded/Ruined BMT).
- **The 4 AU Familiar feats are permanently disabled**: they require Familiar Friend/AU, which no background grants and which is not itself ASI-eligible, so no character can hold it. That is correct, not a bug.

## Feats' additionalSpells (2026-10-08)

- **Catalog** (`catalog/official_source.py::_feat_spells_from_5etools`): each feat gets `innate_spells` (race-shaped entries for fixed spell names), `spell_choices` (`{variant, level, uses, ability, count, filter | from, count_by_level?}`) and `spell_variants` (names, for feats whose multiple `additionalSpells` entries are all named, i.e. mutually exclusive lists). Mechanism mapping: plain list under innate/known = "at-will", under prepared = "prepared"; `daily`/`rest` (any count key, including "1e") = "1/day"; `will` = "at-will"; `ritual` = "ritual". `ability: "inherit"` stays literal and is resolved at sheet time to the ability the feat increased (`<prefix>:ability-bonus` choice). Backgrounds also carry `feat_variant_hints` (e.g. Acolyte/XPHB grants "magic initiate; cleric", so only Cleric Spells is offered).
- **Resolve** (`engine/resolve.py`): `_feat_innate_spells` appends feat entries (tagged `featId`) to `sheet.innateSpells`; `_feat_spell_choice_templates` builds `<prefix>:spell-variant` and `<prefix>:spell-choice-<i>` Choices (query filters by level/class/school/ritual via `_spell_filter_options`; shape L choose-from-list; Ritual Caster XPHB's level-scaled count via `count_by_level`, treated as count-variable so an over-count is pruned, not a problem). Dependent choices exist only for the selected variant; cid indices cover the full list so they stay stable across variants. Innate spells are not filtered by character level (same as races). New pending spell choices block export until filled. Innate spells now also appear in the YAML, Markdown and PDF exports (this also surfaces race innate spells).
- **Spellcasting ability rule** (`official_source._feat_spell_ability_override`): the feat's own text decides. If it says the spellcasting ability is "the ability increased by this feat" (`_INHERIT_ABILITY_RE`) and the feat has an ability increase, missing/`choose` abilities become `"inherit"` (fixed abilities are never overridden): Cloying Mists, Light Bringer, Treacherous Allure, Vampire Touched, Ritual Caster, Cold Caster, Enclave Magic. If it says the ability is "chosen for your ... feat" (`_SAME_AS_FEAT_ABILITY_RE`) and the prerequisites name exactly one feat, every entry gets `{"sameAsFeat": "<feat index>"}` (Magic Connoisseur -> `magic-initiate-xphb`). Feats whose data keeps a `{choose: [...]}` list (Magic Initiate XPHB, the EFA Marks, etc.) get a real Choice `<prefix>:spell-ability` (`_feat_spell_choice_templates`, emitted whether or not a variant is picked; works for background-granted and ASI-picked feats); until picked, sheet entries carry the open `{"choose": [...]}`. Pending `spell-ability` choices block export like any other pending choice. `sameAsFeat` resolves to the other held feat's ability (following its `spell-ability` pick) and to `None` if that feat is not held (possible when feat prerequisites are off).
- **Known gaps**: Magic Connoisseur's spell LIST does not yet follow Magic Initiate's chosen variant (disclosed gap); Warlike Familiar (AU) has the same wrong `inherit` as Magic Connoisseur had but is unreachable, so it is left as is.
- **Not modelled, on purpose**: `expanded` (the 12 Marks' list expansion), slot-level `sN` keys (8 UA Adept feats), Rune Shaper (rule is "half proficiency bonus" but data lists 14 runes), spell attack/DC for innate spells, short-rest cadence of "rest" wrappers (treated as 1/day), the lossy Cloying Mists/Treacherous Allure/Vampire Touched "prepared" mapping, and Cold Caster's second entry (an unnamed multi-entry feat keeps only its first entry). 11 of 129 fixed spell names are not in the bundled SRD spell list; they keep their name with `spellId: null`.

## Class resources, 2024 chassis and small gaps - R1 (2026-10-09)
- **R1 resource framework, Barbarian and Rogue (done, decisions D1 = `derived.classResources`, D2 = mixed uses SRD numbers).** `derived.classResources` is a flat list in class order (a class's subclass entries follow its own). Shape: `{id "<class>:<name-slug>", classId, source {kind class|subclass, id, label}, name, uses, unlimited? (only when true; uses is then null), recharge long|short|short-or-long|null, die?, dice?, pool?, bonus?, dc?, details?}`; optional fields that are None are omitted. Barbarian gives `Rage` (`uses`, `recharge "long"`, `details {damageBonus, resistances [bludgeoning, piercing, slashing]}`); Rogue gives `Sneak Attack` (`dice "NdF"`, `uses` null, `recharge` null).
- **Loader.** `official/subclasses.load_class_2024_tables(class_dir)` -> `{class: {column slug: [20 values]}}` from the XPHB `classTableGroups` and `load_subclass_2024_tables` -> `{subclass id: {...}}` from `subclassTableGroups` (ids use `_sub_id`, e.g. `psi-warrior-xphb`). Groups without exactly 20 `rows` (the `rowsSpellProgression` slot tables) are skipped, so are columns whose label has a `|spells|` filter, "Spell Slots" and "Slot Level". Label slug: `{@filter X|..}` / `{@tip X|..}` -> X. Values: digit strings -> int, `{type: bonus|bonusSpeed}` -> value, `{type: dice}` -> `"NdF"`, `{@dice D6}` -> `"d6"`. `Catalog.class_2024_tables` / `subclass_2024_tables` (default `{}`) are filled next to `class_2024_progressions`. Real columns: barbarian rages / rage-damage / weapon-mastery; bard bardic-die; cleric, paladin channel-divinity; druid wild-shape; fighter second-wind / weapon-mastery; monk martial-arts / focus-points / unarmored-movement; ranger favored-enemy; rogue sneak-attack; sorcerer sorcery-points; warlock invocations.
