# Architecture: offline engine and PWA

_Service extraction, the offline build, the worker, the lazy PDF stack, the PWA and the Pages deploy (O0 to O5). Moved verbatim._

## O0 service extraction (2026-11-05)

- **What.** Slice O0 of docs/superpowers/plans/2026-11-04-offline-pyodide.md. No behaviour change, no data change, golden, frozen snapshots and `export_baseline.json` untouched. Every route body of `server/app.py` moved into the framework-free `server/service.py`: `handle(method, path, query, body) -> (status, content_type, headers, body_bytes)`. `app.py` is now a thin Flask adapter (about 90 lines): it registers the rules of `service.ROUTES` with one view that calls `service.handle`, and keeps the 1 MB limit (413 through `MAX_CONTENT_LENGTH`), flask-cors, the static SPA catch-all, the JSON errorhandler for Flask's own failures, the startup log line and the `__main__` / waitress entry points. `app` re-exports `_catalog`, `_spells_by_class`, `_spell_items`, `_pending_export_problems`, `API_VERSION`, `DRAFT_VERSION` (tests and `i18n_zoo` read them there).
- **service.py contract.** `method` (case-insensitive, HEAD = GET), `path` (decoded, no query), `query` (None, a query string with or without `?`, bytes, or a mapping whose list values give their first item; the first value of a repeated name wins), `body` (None, bytes, str, or a zero-argument callable). The callable is only called by `POST /api/resolve` and `POST /api/export/<fmt>`, after their `lang` check, which is exactly when Flask first read the body; the adapter passes one only when the request is JSON (`request.is_json`, as `get_json(silent=True)` required) and wraps a failed read in `service.BodyReadError`, which `handle` lets through and the adapter re-raises as the original `RequestEntityTooLarge` (so the 413 stays Flask's, and a bad `lang` with a 2 MB body is still a 400). JSON replies are `json.dumps(sort_keys=True, ensure_ascii=True, separators=(",", ":"), default=<Flask's default>)` plus a newline, `Content-Type: application/json`; `service.pretty_json` (set from Flask's debug flag) switches to indent 2 as `jsonify` does. Exports: `text/markdown; charset=utf-8`, `application/x-yaml`, `application/pdf` and `Content-Disposition: attachment; filename*=UTF-8''<quoted name>.<ext>`. An exception inside a route is logged (logger `service`) and answered as the JSON 500.
- **Routing details that were Flask's and are reproduced.** A GET that no route takes under `/api/` is `404 {"error": "not found"}` (this includes a GET of `/api/resolve` and `/api/export/<fmt>`: Flask fell through to the SPA catch-all); a non-GET method on a path/method pair with no route (POST to a GET-only route, POST/DELETE/PUT/PATCH to an unknown `/api/` path) is `405 {"error": "The method is not allowed for the requested URL."}` and carries no `Allow` header (the JSON errorhandler drops it); a trailing slash, an empty or percent-encoded-slash id are 404. Not in the service: OPTIONS and CORS (Flask / flask-cors), non-`/api/` paths (the service answers 404 `not found`; the SPA is the adapter's), the doubled-slash redirect of Werkzeug, and the 413.
- **Tests.** (1) *Committed before the refactor:* `server/tests/service_requests.py` (138 fixed requests: health, resolve with every body shape / content type / lang, catalog and class variants, background / species, items, spells with every `level` form, spell detail, the three exports with lang, gate, name and body cases, unknown ids and formats, wrong methods) + `test_service_baseline.py` + `service_baseline.json` (status, Content-Type / Content-Disposition, sha256 and length of the body; PDFs normalised for `/CreationDate` and `/ID`; skipped unless the bundled data is active; `WRITE_SERVICE_BASELINE=1` regenerates on purpose); it passed unchanged after the refactor. It also pins the 500 (patched `resolve`) and the 413. (2) `server/tests/test_service.py`: `service.handle` equals the Flask test client for every request of the list (status, content type, Content-Disposition, no other header, body bytes, PDFs normalised), the Flask `/api` rules equal `service.ROUTES` (rules and methods), the 500 for both POST routes and a GET route, the lazy body callable and `BodyReadError`, the query / body / method forms, Flask-style JSON, and the isolation pair: an AST check that `service.py` imports no Flask / werkzeug / waitress / pypdf / pytest and nothing but the stdlib and the first-party packages, and a subprocess that blocks `flask`, `flask_cors`, `werkzeug`, `jinja2`, `click`, `itsdangerous`, `blinker`, `waitress`, `pypdf`, `pytest` at the import system, imports `service` and answers health, resolve, a spell, the PDF export gate and a 404 (engine + catalog + service run on stdlib + pyyaml + fpdf2 [+ Pillow, fonttools, defusedxml as fpdf2's own deps]). (3) Moved with the code: monkeypatches of `app.resolve` became `service.resolve` (`test_i18n_messages`, `test_normalize`, the baseline), the AST guards of `i18n_zoo` / `test_i18n_problems` scan `service.py` instead of `app.py`, the root `tests/test_chargen_isolation.py` knows `service`, `test_service`, `service_requests`, `test_service_baseline`.
- **Gate.** server `-n auto` 8414 passed + 3 skipped (was 8233 at N1; +155 new here), `DND_OFFICIAL_DATA=none` 2147 passed / 6020 skipped, root suite 363 passed / 8 skipped, frontend build + vitest 327 passed.
- **Next (O1).** `scripts/build_offline.py` can ship `server/service.py` with the engine and catalog and call `service.handle` from Pyodide; the worker transport maps `{method, path, query, body}` to it directly (body as bytes, no callable needed).

## O2 worker + transport (2026-11-05)

- **What.** Slice O2 of docs/superpowers/plans/2026-11-04-offline-pyodide.md. The app can now run with no server: the engine (Pyodide, the O1 pack) runs in a module Web Worker and answers the same `/api` calls. Python, data, golden, frozen snapshots and `export_baseline.json` untouched; `npm run dev` / `npm run build` still talk to Flask exactly as before.
- **Files.** `frontend/src/api/transport.ts` (`apiFetch(input, init) => Promise<Response>`, fetch's signature plus `timeoutMs` in `ApiInit`; selection; the status store the UI reads), `api/workerTransport.ts` (request mapping, `Response` building, boot wait, timeout, abort, fallback), `api/engineCore.ts` (Pyodide boot and `service.handle` bridge; takes an `EngineIO` so the browser worker and a Node test run the same code), `api/engineHost.ts` (the worker's message loop), `api/engineProtocol.ts` (messages and `EngineSnapshot`), `api/engineStatus.ts`, `api/useEngineStatus.ts`, `engine.worker.ts` (glue, built by vite as a separate 2 KB chunk), `frontend/.env.offline`, npm scripts `build:offline` and `dev:offline` (`--mode offline`), tests `api/workerTransport.test.ts`, `api/transport.test.ts`, `offline/transport.engine.test.mjs`.
- **Call sites.** The 7 sites plus the SK9 health read use `apiFetch`: `useResolution`, `useCatalog`, `ClassPage`, `useItems`, `useSpells` (list and detail), `ExportPage`, `useServerHealth`. `main.tsx` calls `startEngine()` so the worker boots while the first screen is drawn.
- **Selection.** Plain fetch unless ALL hold: the build flag `VITE_OFFLINE_ENGINE` is on (`1|true|on|worker`; only `--mode offline` sets it), `WebAssembly` and `Worker` exist (iOS Lockdown Mode removes WebAssembly), and `<base>pyodide/pack.json` is served as the pack's JSON (the SPA's index.html answered with 200 does not count). If the worker cannot be created or its boot fails, the pending calls and every later one go to plain fetch (`engine: "fallback"`). `chooseEngine` is a pure function with a truth-table test.
- **Worker.** Boots from same-origin `/pyodide/` only: `pyodide.mjs`, pyyaml, `app.zip`, fonts, the PDF wheels (all at boot for now; O3 makes the PDF part lazy), then imports `service` through a 3-line Python bridge (`engine_call` -> `service.handle(method, path, query, body.to_bytes())`). Requests run one at a time; between two the loop yields so a "cancel" of a queued request is seen. The page sends `{method, path (percent-decoded), query (the `?...` string), body bytes}`; as in the Flask adapter a body is passed only when the request is declared JSON. The reply `(status, content_type, headers, bytes)` becomes `new Response(bytes, {status, headers})` with `Content-Type` and `Content-Disposition`, so `resp.json()`, `resp.blob()` and `resp.ok` behave as with the network.
- **Error shapes (what the UI already handles).** Abort: a DOMException `AbortError` (the late reply is dropped, a `cancel` message removes a still-queued job). Timeout: a DOMException `TimeoutError`; `useResolution` passes `timeoutMs: 30000` (it no longer runs its own timer) and maps `isTimeoutError` to `net.timeout`; in the worker transport the 30 s clock starts only when the booted engine receives the request, so a slow first start cannot time out a request; plain fetch counts from the call. An engine that crashes or fails a request: `TypeError`, which the sites already show as `net.offline` / `export.offline`. Python errors are the service's own JSON 400/404/500 with the same status.
- **Engine starting.** `useEngineStatus()` (`useSyncExternalStore`) gives `{engine: off|starting|ready|fallback, pdf: idle|loading|ready}`. While `starting`, `StatusBanner` shows `<p class="status-banner" role="status" data-state="engine-starting">` with `status.engineStarting` (bg and en); no design.
- **Tests.** vitest (fake worker): Response mapping (status, headers, bytes, blob, 4xx JSON), request mapping, boot wait, timeout after boot only, per-call timeout, abort before boot / before send / after send, boot error and missing Worker fall back, crash and per-request failure are `TypeError`, plain-fetch timeout; selection truth table, `detectPack` (SPA html, 404, network error, base URL), `createApiTransport` (flag off never detects or spawns). Real engine: `offline/transport.engine.test.mjs` runs the same `engineCore` + `engineHost` on Pyodide in Node behind an in-process worker stand-in and checks health, resolve, catalog / class / spells, the 400 / 404 shapes, Markdown / YAML / PDF with `Content-Disposition`, and abort. The O1 equivalence test (golden, 52 export hashes, 137 requests) is unchanged and still runs.
- **Browser check (Claude browser pane, Chromium, 375 px).** `npm run build:offline`, `vite preview` on port 4175 (a Flask from an earlier session was still listening on 8000 and was left alone; the proof is that the page made no `/api/` request at all, by resource timing), the class list came from the worker, a Fighter picked and the sheet showed "Fighter 1" with the right numbers; the engine-starting line showed during the first moments in Bulgarian ("Стартира се двигателят на приложението…") and in English ("Starting the app engine…") and vanished when ready. The default dev server (port 5173) still calls `/api/*` as before.
- **Test fix found on the way.** `server/tests/test_service_baseline.py` hashed the live `frontend/dist/index.html` for `GET /api` (Flask's SPA catch-all), so any frontend build moved it (the content-hashed asset names). It now serves `server/tests/spa_dist/index.html`, the index.html of the O0-time build (rebuilt from commit `e96c184`'s frontend: sha256 `39a041c4...` equals the baseline), through `app.config["FRONTEND_DIST"]`; `service_baseline.json` is unchanged.
- **Not done here.** PWA / service worker / precache (O4); the PDF stack is still loaded at boot (O3).

## O3 lazy PDF stack (2026-11-05)

- **What.** Slice O3 of docs/superpowers/plans/2026-11-04-offline-pyodide.md. The PDF stack (fpdf2, Pillow, fonttools, defusedxml, plus the fonts) is no longer needed to start the engine: `server/service.py` imports `pdf_export` inside the PDF renderer (`_render_pdf`, called by the export route after the export gate), not at module level. Engine, catalog, resolve, YAML and Markdown work without the four packages; a PDF render without them is the service's JSON 500 (the generic handler). Flask behaviour and every response are unchanged (service-vs-Flask equality over 137 requests and the O0 baseline pass as they were); golden, snapshots and `export_baseline.json` untouched.
- **Worker.** `engineCore.boot()` now loads Pyodide, pyyaml and `app.zip` only; `preparePdf()` unpacks `fonts.zip` and loads the four wheels once (the promise is shared, dropped on failure so a retry works). `engineHost` serialises it with requests: a `prepare` message answers `prepared` or `prepare-error`. The transport sends `prepare` the first time it sees `POST /api/export/pdf` (`needsPdfStack`), sets `pdf: "loading"` (shared by concurrent exports), sends the request only when the stack is there, and starts that request's 30 s clock after the preparation (same rule as the boot). An abort during the preparation rejects with `AbortError` while the load goes on (the next export reuses it); a failed load is a `TypeError` (`export.offline` in the UI) and the state returns to `idle` so the next export retries.
- **Flag for O4.** `VITE_OFFLINE_PDF=eager` (build-time, read in `engine.worker.ts`; default lazy): the host starts the same load right after `ready` and announces it (`preparing`, then `prepared`), so the page's `pdf` state and a waiting export follow it; nothing else changes. O4 sets it once the service worker precaches `fonts.zip` and the wheels, so the first PDF is instant and works offline from the start; without it the files are fetched on the first PDF (which also works offline once they are in the cache).
- **UI.** `useEngineStatus().pdf === "loading"` shows `<p role="status" data-state="preparing-pdf">` on the Export page with `exportPage.preparingPdf` (bg "Подготвя се PDF…", en "Preparing the PDF…"); no design. Browser check at 375 px (offline build, preview server): the line showed for about 0.14 s on the first PDF in both languages and the export finished with no `/api` request; a second PDF in the same session does not show it.
- **Tests.** Python: `test_service.py::test_everything_but_a_pdf_works_without_the_pdf_stack` (subprocess with `fpdf`, `PIL`, `fontTools`, `defusedxml` blocked by a meta-path finder: health, catalog, class page, items, spells, resolve, YAML, Markdown in both languages, the PDF gate's 400 and an unknown path all answer and none of the four modules is loaded; a real PDF render is the JSON 500) and `test_service_does_not_import_the_pdf_stack_at_module_level` (AST). vitest: fake-worker tests for the PDF state machine (only the PDF export asks, one load for concurrent exports, timeout excludes the preparation, abort, failure and retry, eager mode, an export during the eager load waits) and `engineHost.test.ts` (lazy / eager, prepare, prepare-error, cancel). The Node equivalence test (O1) no longer loads the PDF stack at boot: it asserts `service` imports and serves catalog and spells with none of the four modules in `sys.modules`, then loads fonts + wheels on demand (91 ms) before the export and request parts, which compare exactly what they compared before (251 golden, 52 export hashes, 137 requests); `transport.engine.test.mjs` checks `pdf` is `idle` after Markdown / YAML exports and goes `loading -> ready` on the first PDF.
- **Note.** The Node tests run the built pack: after changing anything under `server/` rebuild it (`.venv/bin/python scripts/build_offline.py`; `app.zip` is deterministic).

## O4 PWA: installable, offline after the first visit, sub-path ready (2026-11-10)

- **What.** Slice O4 of docs/superpowers/plans/2026-11-04-offline-pyodide.md, with the owner's hosting decision of 2026-11-10 (GitHub Pages, public repo, free plan, served under `/dnd-character-creator/`). Frontend only: Python, data, golden, frozen snapshots and `export_baseline.json` untouched. The default `npm run build` / `npm run dev` (Flask) are unchanged apart from the Help link and the base-path plumbing (default base `/`); no service worker is registered there.
- **Base path.** `vite.config.ts` reads `VITE_BASE` (default `/`; a value like `/dnd-character-creator/` is normalised to start and end with `/`, anything else throws) and sets vite's `base`. Everything follows `import.meta.env.BASE_URL`: asset URLs, the engine worker (`BASE_URL + "pyodide/"`), `detectPack`, `<BrowserRouter basename>`, the service worker URL and scope; the manifest uses only relative URLs (`start_url`, `scope`, `id` = `./`, icons relative). Deviation from the brief ("default './'"): a relative base breaks the worker URL and `pack.json` detection on deep links with the history router, so the default stays `/` (Flask) and the Pages build sets the sub-path.
- **Manifest and icons.** `frontend/public/manifest.webmanifest`: name "Създаване на герои", short name "Герои", `lang` bg, `display` standalone, `theme_color` = `--color-accent` (#2980b9, `index.html`'s theme-color meta moved from #eeeeee to the same), `background_color` = `--color-page`. Icons are functional placeholders generated by `scripts/make_pwa_icons.py` (a white hexagon on the accent colour; pure stdlib, no Pillow): `icon-192/512.png`, `icon-maskable-192/512.png`, `apple-touch-icon.png` (180). `index.html` links the manifest and the icons and has the iOS tags (`apple-mobile-web-app-capable`, title, status bar style; vite prefixes the base path).
- **Service worker (hand-written, no new dependency).** `frontend/pwa/sw.template.js` + `frontend/pwa/precache.mjs` (builder and vite plugin, plain ESM with a `.d.mts`). After an offline-mode build (`VITE_OFFLINE_ENGINE` on and `dist/pyodide/pack.json` present) the plugin writes `dist/sw.js`: the manifest of EVERY file of dist except `sw.js`, `404.html`, source maps and `.DS_Store` (23 files, 18.30 MB: app shell, manifest, icons, engine worker, and the whole pack incl. `pack.json`, wheels, `fonts.zip`), each with a revision (first 16 hex of its sha256), and `version` = hash over all paths and revisions (the cache name `dnd-builder-precache-<version>`; the same inputs give the same version). It also copies `index.html` to `404.html` (GitHub Pages answers an unknown path with it, so a deep link still loads the SPA). No Workbox, so no 2 MiB `maximumFileSizeToCacheInBytes` limit applies (the 9.6 MB wasm is precached like any file). Worker behaviour: install downloads all files (4 at a time, `cache: "no-cache"` so a copy the page just downloaded is revalidated, not fetched again), files already in an older cache under the same revision are copied locally (an update re-downloads only what changed), one failure fails the install and a retry resumes; a new version WAITS (no automatic `skipWaiting`) until the page sends `SKIP_WAITING`; activate deletes older `dnd-builder-precache-*` caches and claims the pages; fetch answers same-origin GETs in scope from the cache (cache-first), a navigation in scope gets `index.html`; `/api`, other origins, non-GET and Range go to the network. All URLs resolve against the registration scope, so any sub-path works. Not done: integrity check of a downloaded file against its revision (a stale CDN edge during a deploy could cache a mismatching file; the next version change replaces it).
- **Page side.** `src/pwa/register.ts` (pure state machine over injected objects: phase `unsupported | idle | installing | offline-ready | update-available | error`, `justReady`, `persisted`; registers with `updateViaCache: "none"`; reloads only after the user asked for the update and the controller changed), `pwaStore.ts` (`usePwa`, `startPwa`: production builds only, started by `main.tsx` only when the transport chose the in-browser engine, checks for a new version whenever the page becomes visible), `requestPersistence` (calls `navigator.storage.persist()` once when offline-ready; granted / denied / unsupported shown on Help). `StatusBanner` lines: `pwa-installing`, `offline-ready` (once per visit after the first install, dismissable), `update-available` + button, `engine-unavailable`. Help page `/help` (link `.help-link` in the header; plain text, bilingual `copy.help` / `copy.pwa`): offline status, install steps for iPhone Safari (Share > Add to Home Screen), Android Chrome and desktop, the 7-day storage eviction warning with a link to the library export on Home, Lockdown Mode and cache-reset troubleshooting. `bg-render.json.gz` was re-captured on purpose: the only difference in all 80 captured pages is the added header link (`<a class="help-link" ...>Помощ</a>`, proven by stripping it and comparing with the old snapshot).
- **Serverless engine.** `VITE_SERVERLESS=1` (set by the Pages build): `createApiTransport({serverless})`; a missing WebAssembly / Worker (iOS Lockdown Mode), an unreachable pack or a failed worker give `EngineState` `"unavailable"` and every `apiFetch` rejects with a `TypeError` (the pages already show it as a lost connection) instead of asking the static host for `/api/...`.
