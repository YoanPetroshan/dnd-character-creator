## RP6 (P0) Golden rebaseline mode (2026-10-23)

Tests only. `server/tests/test_c_series_golden.py` gains `--rebaseline <SLICE> [--dry-run]`, the append-only constant `REBASELINES` (empty today) and the function `rebaseline()`. The real golden gz is byte-identical (no rebaseline was run); `STRIP` stays `("derived.featResources",)`. The module docstring explains the workflow.

- **Entry.** `REBASELINES[slice] = {"cases": [fnmatch over case names], "paths": [regexes over normalized paths], "why": line}`. The `paths` allowlist is written from the slice's rule matrix, never copied from the dry run; the reviewer compares the two.
- **Algorithm (as in the plan, section 1).** Cases not matching `cases` must re-resolve to the stored result (STRIP applied to both sides) and are written back unchanged. Matching cases: `ks.fill` on a copy of the stored draft (only newly `pending` cards get picks, with the kitchen-sink overrides of that case), re-resolve, then both `{draft, result}` sides are normalized and diffed. Normalization turns every list of dicts that all carry a unique string `id` into a dict keyed by id, so an inserted card is one path (`result.choices[<id>]`, options `...options[<id>]`) and does not shift the others. An added or removed subtree is reported once at its root.
- **Rules.** Any changed path outside `paths`, or an unmatched case that moved, raises `RebaselineError` before anything is written. A matching case with no diff prints a warning (pattern too wide). Cases are never deleted or added (`--append` adds). The gz is written only when a matching case changed (gzip headers would otherwise change the bytes for nothing). The printed summary (changed cases, count per path regex, warnings) goes verbatim into the slice's ARCHITECTURE section.
- **`--dry-run`** prints every changed path per case (marking `DISALLOWED` ones) and writes nothing, and does not raise on violations.
- **Tests (9 new, same file).** A synthetic two-case golden in `tmp_path` through the module-level `GOLDEN` override, with a fake resolver and filler (no catalog involved): expected path passes and writes only the matching case; unexpected path fails and leaves the file untouched; an unmatched case changing fails; dry run writes nothing; warning for an unchanged matching case; inserted card at a keyed path; unknown slice; `REBASELINES == {}` and `STRIP` pinned; normalization and `diff_paths` unit test.
- **Totals.** Server suite 4089 -> 4098 passed (F0 golden green, not regenerated), root suite 405 passed / 8 skipped; frontend untouched.

## W3 (F9) Fuzz / property harness and the non-settling fill (2026-10-24)

- **Harness.** `server/tests/test_resolve_fuzz.py`: `gen_draft(seed, catalog)` is a pure function of `random.Random(seed)` (ruleset 2014 / 2024 / mixed, 1-3 distinct classes with levels summing to at most 20, a random subclass at any level, species with an optional subspecies and a background allowed by the ruleset, half the drafts with a random `sources` subset, base scores 3-18), filled by `kitchen_sink.fill` through a tracing resolve. Properties: resolve never raises (filled and unfilled drafts), resolve twice is byte-identical (`json.dumps(sort_keys=True)`), `fill` settles within 10 rounds (the failure message has the seed, the full draft and the cards still pending), 3 random mutations per settled draft (level-down, class reorder, ruleset / species / background switch) never raise and every stored pick without a card, or selected id outside its options, is listed in `pruned`, yaml / markdown / pdf exports return 200 on up to 10 problem-free settled drafts, the slowest resolve is under 50 ms (a slow draft is re-timed warm, best of 3: the first resolve with a new `sources` set builds the spell-visibility cache; one cold run of 8000 took 66 ms, warm 2.8 ms). Default N=60 adds about 3 s.
- **Bigger runs.** `cd server && FUZZ_N=3000 ../.venv/bin/python -m pytest tests/test_resolve_fuzz.py -q` (3000 drafts about 80 s, 8000 about 190 s); `FUZZ_SEED0=<n>` starts at another seed. No new dependency and no marker (the env var is the switch).
- **Volume run.** Seeds 0..2999 (before the fix) and 0..7999 (after): 0 exceptions, 0 non-idempotent resolves, 0 mutation or export failures. Only F9 below failed.
- **F9 root cause.** The planner's non-settling case was not reproducible with `sources: []` (a targeted sorcerer 5 + wizard 10 scan over 12000 seeds and all three rulesets settled every time). The fuzz found it with a restricted `sources`: seeds 763 and 1366 (mixed, `human-xphb`, sources without any book that has Origin feats). `_species_feat_pool` keeps only feats from the allowed books, so the Human Origin feat card had zero options but stayed `pending`; `fill` stored `[]` forever and export could never succeed (nothing to flip: one card, never fillable). Fix (`class_choices_2024.mark_unavailable`): a pending species feat card with no options at all becomes `unavailable` with a reason, like the F3a cards; cards whose options are merely all disabled (prerequisite / already taken) are untouched. Regression: `test_f9_fuzz_seeds_settle[763|1366]` and a hand-built draft test. Golden unchanged (default sources never hit it). A scan of 1500 seeds for other pending cards with no enabled option found no other source.
- **Not found.** No oscillating pair of cards turned up in 8000 drafts; if the planner's seed 11 was a different (flip) case it is still unreproduced.

## T0 controlled rebaseline of the English message snapshot (2026-11-05)

- **What.** Slice T0 of docs/superpowers/plans/2026-11-05-backend-completion.md. The I1 snapshot (`tests/golden/messages_en_snapshot.json.gz`) was append-only; a slice that deliberately changes engine English text (a new reason, a reworded note) had no sanctioned way to move it. `tests/i18n_zoo.py` now has `--rebaseline <SLICE> [--dry-run]`, mirroring the golden tool (`test_c_series_golden.py`). No engine change; the snapshot content is byte-identical (same JSON; only the gz header timestamp would differ on a rewrite, and nothing was rewritten).
- **Registry.** `SNAPSHOT_REBASELINES` (append-only, empty today): slice id -> `{"cases": [fnmatch over zoo case names], "paths": [regexes over leaf paths], "why": one line}`. The `paths` allowlist is written from the slice's rule, never copied from the dry-run. A leaf path is the position inside a case's leaves: `problems[0][1]`, `pruned[3][1]`, `disabled.<card> | <option>`, `cards.<cardId>[0]`, `exportGate[0][1]` (dict keys joined by `.`, list positions `[i]`; an added or removed key, or a list of another length, is reported at the key or list).
- **Behaviour.** The tool re-resolves every stored case. A change in a case that does not match `cases`, or on a path outside the allowlist, is a violation: `--dry-run` prints it (`DISALLOWED`) and writes nothing, the real run raises `RebaselineError` before writing anything. Matching cases that did not change get a "pattern too wide" warning (first 10 printed). A stored case missing from the zoo is refused (the snapshot only grows, in dry-run too); new zoo cases are not added by a rebaseline (`--append` does that). There is still no regenerate.
- **Usage.** `cd server && ../.venv/bin/python tests/i18n_zoo.py --rebaseline G3 --dry-run`, then without `--dry-run`; extend the pin in `tests/test_i18n_snapshot_rebaseline.py` (`PINNED`) in the same commit and name the rebaseline in the commit message. `tests/test_i18n_snapshot.py` stays the guard (any unlisted diff fails it).
- **Tests.** `tests/test_i18n_snapshot_rebaseline.py` (10, synthetic zoo and a temp file, the real snapshot is never touched): the registry tuple pin (append-only) and entry shape; an unlisted change fails and leaves the file; a change in an unmatched case fails even on an allowed path; a listed change makes the compare fail before and pass after the write; dry-run writes nothing and reports violations; removal of a stored case is refused (dry and real); new zoo cases are not added; unknown slice raises; diff-path shapes; CLI has no regenerate and rejects bad usage.
